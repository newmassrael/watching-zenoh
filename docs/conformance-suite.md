# The zenoh conformance test suite

Status: in progress. The base layer of the requirements covers the transport; the PICS and PIXIT
proformas and wz's PICS answers cover what that part selects and parameterises. The test
purposes, the service primitives and the test management protocol come next (section 7).

## 1. What it is

One conformance test suite for every implementation of zenoh: zenoh-pico, zenoh-c, the Rust
zenoh, wz behind each of its ABIs, and any implementation added later. Adding an implementation
adds an adapter for its API family and the implementation's answers to the PICS; it changes no
test. The verdict of a test comes from a requirement, never from what another implementation
does; a difference between implementations is diagnostic data, reported apart.

The suite follows ISO/IEC 9646 and TTCN-3 (ETSI ES 201 873):

- **The chain.** The conformance requirements (section 3), the test purposes drawn from them, and the abstract
  test suite that realises the purposes, with a PICS proforma (what an implementation is,
  ISO/IEC 9646-7, section 4) and a PIXIT proforma (where it is tested, section 5) beside them.
- **The test method** is the coordinated one (ISO/IEC 9646-2). A lower tester stands in for the
  zenoh nodes the implementation under test talks to, on the wire. An upper tester sits above
  the implementation's public API. A test management protocol carries the lower tester's
  commands to the upper tester over a channel of its own. The upper tester gives no verdicts.
- **The lower tester shares no code with any implementation under test**, its codecs included:
  a codec shared with the implementation would carry the same faults to both sides of the test,
  where they cannot be seen. wz's codecs are generated by SCE, so a tester codec generated by SCE
  from wz's message descriptions is excluded too.
- **The notation** is an SCE test profile document, whose semantics are TTCN-3's (ES 201 873-4).
  Its TTCN-3 export runs on Eclipse Titan beside the native run, and the two runs must agree
  (section 6).

## 2. Where it is

| Path | Holds |
|---|---|
| `conformance/suite/requirements/` | the conformance requirements, one file per part of the base specification |
| `conformance/suite/pics.toml` | the PICS proforma |
| `conformance/suite/pixit.toml` | the PIXIT proforma |
| `conformance/suite/answers/wz.toml` | how a wz build's conformance statement answers the PICS, per ABI |
| `crates/wz-conformance-suite` | reads the files, holds them to their formats and to each other, and answers the PICS of a wz build |

The files are TOML so that the test system reads them as data: the PICS answers select test
purposes, and the PIXIT answers fill in a test environment's parameters. The crate's tests are
the static checks a test system makes before it selects any test (section 3.3, 4.2, 5).

A profile's requirements and its additions to the PICS (a consumer's own evaluation
specification) are kept by whoever owns that specification, outside this repository, in the
same format with `layer = "profile"`.

## 3. The conformance requirements

### 3.1 Two layers

zenoh has no separate normative specification, so the suite writes its own conformance
requirements, and every one cites where it comes from (ISO/IEC TR 10000, ISO/IEC 9646-6):

- **Base.** The pinned upstream release (`base = "zenoh 1.10.2"`). Its protocol definitions and
  its codec fix the wire form. Its documentation and the contract sentences of its public API
  headers fix the meaning of the services.
- **Profile.** A specification that builds on the base. Each of its requirements is one of three
  classes: a `selection` picks an option or fixes a value the base leaves open, an `addition`
  says what the base does not say without contradicting it, and a `deviation` departs from the
  base requirements it names in `deviates_from`. An implementation that follows a deviation
  cannot claim base conformance for those requirements, and the conformance report has a base
  column and a profile column.

What an implementation does is not a source of any layer. When the only text for a rule is an
implementation's behaviour, or when two sources disagree, the requirement carries an `issue`, and
a test of it is inconclusive until the issue is settled.

### 3.2 The format

A file holds `format = "wz-conformance-requirements"`, `format_version = 1`, its `layer`, its
`part` and its `base`, then one `[[requirement]]` table per requirement:

| Field | Holds |
|---|---|
| `id` | unique in the whole list: `B-` for the base, `P-` for a profile, then the area and a number |
| `strength` | `MUST`, `SHOULD` or `MAY` |
| `kind` | ISO/IEC 9646-1's `static` (which capabilities an implementation has and how they combine) or `dynamic` (what it does when it communicates, the encoding of what it sends included) |
| `aspect` | `encoding` (the form of a message) or `procedure` (an exchange, a rule over time or state) |
| `binds` | `sender`, `receiver` or `both`: what an implementation sends, what it accepts |
| `applies` | optional: the PICS selection under which it applies (section 4.1) |
| `text` | the requirement, written so that a codec or a test purpose can be written from it alone |
| `sources` | for the base, anchors into the pinned upstream: `` `<path>` @ `<needle>` ``, the path from the checkout's root; for a profile, the clauses of the profile |
| `issue` | optional: why the sources do not settle it |
| `class`, `deviates_from` | a profile requirement's standing to the base (section 3.1) |

The encoding requirements are the codec input: the whole of what the author of an independent
codec is handed (`Suite::encoding_requirements`).

### 3.3 What is held

`check` refuses: a file of another format; an id that is malformed or stated twice; a
requirement with no text or no source; a base source that is not an anchor under a top-level
directory of the upstream checkout; a base requirement none of whose sources is normative for
its aspect (the protocol definition for a procedure, the definition or its codec for an encoding)
unless it carries an issue; a base requirement with a class; a profile requirement without a
class, a deviation that names no base requirement, and a departure from an id that is no base
requirement; and an `applies` that does not parse or names something other than a support item
of the PICS. Whether each anchor still holds at the pin (the path exists and the needle occurs in
it) is the upstream citation gate's, which grades every tracked file.

### 3.4 Coverage

| Part | File | Covered |
|---|---|---|
| Common encodings, extension chain, batches | `base-transport.toml` | yes |
| Transport: Init, Open, Close, KeepAlive, Frame, Fragment, Join | `base-transport.toml` | yes; OAM is not |
| Scouting: Scout, Hello | | no |
| Network: Push, Request, Response, ResponseFinal, Interest, Declare | | no |
| Zenoh messages: Put, Del, Query, Reply, Err, and the extensions they carry | | no |
| Service semantics: the contract sentences of the public APIs | | no |

The transport part has 49 requirements, 11 of them with an issue. Two issues are disagreements
between sources: the OpenSyn cookie's length bound (B-OPEN-2), and whether a variable-length
integer may be written longer than it needs (B-ENC-2). The rest record rules that only the
pinned implementation states, among them the resolution negotiation (B-INIT-8), sequence numbers
(B-SN-1, B-SN-2) and lease expiry (B-LEASE-1).

## 4. The PICS

### 4.1 The proforma

`pics.toml` holds `format = "wz-conformance-pics-proforma"`, `format_version = 1` and one
`[[item]]` per question:

| Field | Holds |
|---|---|
| `id` | `T-` for the transport, `P-` for the platform |
| `question` | what the implementation answers |
| `status` | ISO/IEC 9646-7's notation: `m`, `o`, `o.<n>` (at least one item of group `n` is supported), `x`, or `c` |
| `condition`, `then`, `else` | for `c`: a selection over other support items, and the status when it holds and when it does not (`n/a` among them) |
| `answer` | `support` (yes or no) or `value` |
| `values` or `min`, `max` | a value item's admitted values, as a list or as an integer range (`max` absent: no upper bound) |
| `unit` | a value item's unit |
| `reference` | the requirements whose selection or value the item decides |

A selection is item ids joined by `and`, `or` and `not`, with parentheses; `and` binds tighter
than `or`. A requirement's `applies`, a conditional item's `condition` and, later, a test purpose's
selection are written in it.

### 4.2 What is held

`check` refuses: an id malformed or stated twice; a status outside the notation; a conditional
item without its condition, `then` or `else`, or whose condition names itself; a condition, `then`
or `else` on an item that is not conditional; a group with one item; a support item with values,
a range or a unit; a value item with neither a list nor a range, with both, or with `max` below
`min`; and a reference to no requirement, or to one that does not exist.

### 4.3 wz's answers

A wz build states what it is in its conformance statement (decision C15 of
`docs/build-configuration.md`), and each C ABI library carries the statement's digest, so the
test system can check that the build it talks to is the one the statement describes.
`answers/wz.toml` says, per ABI (`pico`, `c`), how the statement answers each item, in exactly one
way: a `capability` (supported when the statement says so), a `limit` (its value), a `policy` with
a `map` from every value the policy takes to an admitted answer, a `fixed` answer with `why`, or
`unanswered` with what the statement lacks. `answer()` reads a statement through it.

`check_answers` refuses a row of another ABI; an item the proforma does not have; a row that
answers in none or several ways; a `why` without a fixed answer or a fixed answer without one; a
map without a policy; a capability the declaration does not have, or does not export for the
row's ABI; a limit or policy the declaration does not have; a capability that answers a value
item, or a limit or policy that answers a support item; a map that does not cover the policy's
values exactly, or maps one to an answer the item does not admit; a fixed answer the item does not
admit; and an item that is not answered exactly once for each ABI.

What the statement cannot answer today, and so what it would have to carry for the test system to
read the whole PICS from the build:

| Item | pico ABI | zenoh-c ABI |
|---|---|---|
| T-ROLE-ROUTER | the `peer` capability admits the router mode's name; whether that mode forwards is not stated | answered (`router-node`) |
| T-STREAM-LINK | no capability names the tcp link | the same |
| T-COMPRESSION | not one of this ABI's capabilities | answered (`transport_compression`) |
| T-PATCH | the patch the sessions advertise | the same |
| T-RID-RES | the request id resolution | the same |
| T-BATCH-UNICAST, T-BATCH-MCAST, T-LEASE, T-KA-PER-LEASE, T-FRAG-MAX | answered (the `PICO_` limits) | read from the session's configuration when it opens, which the statement does not carry |

## 5. The PIXIT

`pixit.toml` holds `format = "wz-conformance-pixit-proforma"`, `format_version = 1` and one
`[[item]]` per question: `id` (`X-`), `question`, `answer` (`text`, `integer` or `choice` with its
`values`), `unit`, and `distinct_from`, another item whose answer this one's must differ from. The
items are the test method, the locators of both ends of the test link, the interface of the test
link and the channel of the test management protocol (which must not be the same interface: a port
of the same interface still shares its queues, its buffers and its processor with the test link),
the upper tester's share of the implementation's resources, how the test system slows the test
link below the implementation, and the timer tolerance.

`check` refuses an id malformed or stated twice, a choice without values, values on another kind,
and a `distinct_from` that names the item itself or no item.

## 6. What the suite takes from SCE, and what it asks of it

SCE decides the notation and the second executor in its ADR 0091; the TTCN-3 lane lives in a
separate repository (`sce-ttcn3-titan`) under EPL-2.0. wz depends on the surfaces SCE publishes for
it and on nothing else of SCE.

### 6.1 What the suite takes

| Surface | Used for |
|---|---|
| the test profile (`SCE_TEST_PROFILE.md`): the `test-` kinds, templates, ports, timers, defaults, components, verdicts | the abstract test suite |
| features selecting test cases (`--world <feature>,...` of each runner) | PICS support items: the test purposes a PICS answer selects |
| module parameters (`--module-parameter <id>=<value>`) | PICS value items and PIXIT items |
| `sce-codegen export-ttcn3` and `sce-ttcn3-validate` | the TTCN-3 suite and its correspondence check |
| each backend's runner of a generated suite | the native executor |
| the canonical log `sce-test-log.v1` | the comparison of the two runs |
| the recorded input trace `sce-test-trace.v1`, and the downstream's recorder | replaying a live run's inputs into the second executor |
| codec documents (`SCE_FORGE.md`, the codec kind) | the native lower tester's codec, written from the encoding requirements of section 3 and never from wz's message descriptions |

### 6.2 What the suite needs that the surfaces do not yet give

1. **A codec for positional binary messages on the TTCN-3 side.** The lane binds only CBOR and
   content-line formats, each over a library neither SCE nor Titan wrote. zenoh's messages are
   positional binary with variable-length integers. The suite brings its own TTCN-3 types module
   for them, written clean-room from the encoding requirements, encoded by Titan's RAW engine and
   by external functions for what RAW cannot express (variable-length integers, extension chains
   delimited by a flag). The lane's entry for a suite has to be able to name such a consumer
   codec for a mapped type instead of an SCE codec document.
2. **The wire bytes in the trace, decoded on both sides.** A trace record holds the decoded
   value, and in the lane the native side uses no codec. The suite's third condition is that the
   two independent codecs read the same wire bytes to the same value. So a lower-tester port has
   to carry the encoded octets, recorded as such, with each executor decoding them with its own
   codec, and the canonical log recording the decoded value beside them.
3. **A recorded live run.** Against a live implementation the two executors cannot be fed the same
   inputs live. The native executor runs against the implementation, the recorder writes the
   trace (at the octet level of item 2), and the TTCN-3 executor replays it. The recorder must
   record what arrives on every mapped port, the test management protocol's port included.
4. **The name rule from a PICS item to a feature.** PICS ids are upper-case with hyphens. The
   suite needs the grammar of a feature name and of a module parameter name, so that the mapping is
   one rule and not a table.
5. **The test management protocol's encoding.** Both executors drive the same upper tester, so
   both need its codec. The protocol is to be encoded in CBOR and described by an SCE codec
   document, which the lane already binds on the TTCN-3 side (libcbor); this asks nothing new of
   the lane, provided the CBOR binding covers the shapes the protocol uses.

### 6.3 What the suite gives

The abstract test suite and its lane entries, its traces and expected logs, and the zenoh types
module and external functions of item 1. Where the parts that are compiled and linked with Titan
live, and under which licence, is open (section 8).

## 7. Steps

The wz side, in order. A step that needs nothing of SCE is marked so.

1. The conformance requirements, base layer, transport part; the PICS and PIXIT proformas for it; wz's
   answers to the PICS. Done (needs nothing of SCE).
2. The other parts of the base layer: scouting, network, zenoh messages, service semantics, each
   with its PICS items (needs nothing of SCE).
3. Test purposes: for each requirement or group of requirements, what is checked: the
   requirements, the PICS selection, the initial state, the stimulus and the expected
   observation, with no executor's vocabulary (needs nothing of SCE).
4. The abstract service primitives and the test management protocol: the primitives the upper
   tester offers, derived from zenoh's services and not from one API; handles the upper tester
   assigns; the first exchange of version, PICS answers and build digest; indications as a timed
   event stream; idempotent commands; a reset to idle (needs nothing of SCE but item 5 of
   section 6.2 for its encoding).
5. The independent codecs: the TTCN-3 types module, written by a separate author from the
   encoding requirements alone, and the native codec documents, written from the same
   requirements by the same rule. Validation by the round trip of captures from two or more
   implementations, and by differential fuzzing of the two codecs (needs items 1 and 2 of section
   6.2 to run in the lane; the writing needs nothing).
6. The upper tester's common part and one adapter per API family (pico API, zenoh-c API, Rust
   API).
7. The abstract test suite, as test profile documents; the lane entries; the first runs against
   zenoh-pico and wz (needs section 6.2).
8. The statement's gaps of section 4.3 closed, so that the whole PICS of a wz build is read from
   the build.
