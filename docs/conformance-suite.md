# The zenoh conformance test suite

Status: in progress. The base layer of the requirements covers the transport and the network;
the PICS and PIXIT proformas and wz's PICS answers cover what those parts select and
parameterise; the test configurations, the first test purposes, the abstract service primitives
and the test management protocol are stated. The abstract test suite itself, in the SCE test
profile, comes next (section 11).

## 1. What it is

One conformance test suite for every implementation of zenoh: zenoh-pico, zenoh-c, the Rust
zenoh, wz behind each of its ABIs, and any implementation added later. Adding an implementation
adds an adapter for its API family and the implementation's answers to the PICS; it changes no
test. The verdict of a test comes from a requirement, never from what another implementation
does; a difference between implementations is diagnostic data, reported apart.

The suite follows ISO/IEC 9646 and TTCN-3 (ETSI ES 201 873):

- **The chain.** The conformance requirements (section 3), the test purposes drawn from them
  (section 7), and the abstract test suite that realises the purposes, with a PICS proforma (what
  an implementation is, ISO/IEC 9646-7, section 4) and a PIXIT proforma (where it is tested,
  section 5) beside them.
- **The test method** is the coordinated one (ISO/IEC 9646-2). A lower tester stands in for the
  zenoh nodes the implementation under test talks to, on the wire. An upper tester sits above
  the implementation's public API. A test management protocol carries the lower tester's
  commands to the upper tester over a channel of its own (section 8). The upper tester gives no
  verdicts.
- **The lower tester shares no code with any implementation under test**, its codecs included:
  a codec shared with the implementation would carry the same faults to both sides of the test,
  where they cannot be seen. wz's codecs are generated by SCE, so a tester codec generated by SCE
  from wz's message descriptions is excluded too.
- **The notation** is an SCE test profile document, whose semantics are TTCN-3's (ES 201 873-4).
  Its TTCN-3 export runs on Eclipse Titan beside the native run, and the two runs must agree
  (section 6).

| `conformance/suite/asp.toml` | the abstract service primitives |
| `conformance/suite/tmp.toml` | the test management protocol |
| `crates/wz-conformance-suite` | reads the files, holds them to their formats and to each other, and answers the PICS of a wz build |

The files are TOML so that the test system reads them as data: the PICS answers select test
purposes, and the PIXIT answers fill in a test environment's parameters. The crate's tests are
the static checks a test system makes before it selects any test (sections 3.3, 4.2, 5, 7, 8).

A profile's requirements and its additions to the PICS (a consumer's own evaluation
specification) are kept by whoever owns that specification, outside this repository, in the
same format with `layer = "profile"`.

Everything here is in this repository because none of it is compiled or linked with the TTCN-3
tool. What is goes elsewhere (section 10).

## 3. The conformance requirements

### 3.1 Two layers

zenoh has no separate normative specification, so the suite writes its own conformance
requirements, and every one cites where it comes from (ISO/IEC TR 10000, ISO/IEC 9646-6):

- **Base.** The pinned upstream release (`base = "zenoh 1.10.2"`). Its protocol definitions and
  its codec fix the wire form. Its key expression library and the documentation of its public API
  are the contract of its services.
- **Profile.** A specification that builds on the base. Each of its requirements is one of three
  classes: a `selection` picks an option or fixes a value the base leaves open, an `addition`
  says what the base does not say without contradicting it, and a `deviation` departs from the
  base requirements it names in `deviates_from`. An implementation that follows a deviation
  cannot claim base conformance for those requirements, and the conformance report has a base
  column and a profile column.

What an implementation does is not a source of any layer. When the only text for a rule is an
implementation's behaviour, or when two sources disagree, the requirement carries an `issue`, and
a test of it is inconclusive until the issue is settled.

### 3.2 The format

A file holds `format = "wz-conformance-requirements"`, `format_version = 1`, its `layer`, its
`part` and its `base`, then one `[[requirement]]` table per requirement:

| Field | Holds |
|---|---|
| `id` | unique in the whole list: `B-` for the base, `P-` for a profile, then the area and a number |
| `strength` | `MUST`, `SHOULD` or `MAY` |
| `kind` | ISO/IEC 9646-1's `static` (which capabilities an implementation has and how they combine) or `dynamic` (what it does when it communicates, the encoding of what it sends included) |
| `aspect` | `encoding` (the form of a message) or `procedure` (an exchange, a rule over time or state) |
| `binds` | `sender`, `receiver` or `both`: what an implementation sends, what it accepts |
| `applies` | optional: the PICS selection under which it applies (section 4.1) |
| `text` | the requirement, written so that a codec or a test purpose can be written from it alone |
| `sources` | for the base, anchors into the pinned upstream: `` `<path>` @ `<needle>` ``, the path from the checkout's root; for a profile, the clauses of the profile |
| `issue` | optional: why the sources do not settle it |
| `class`, `deviates_from` | a profile requirement's standing to the base (section 3.1) |

The encoding requirements are the codec input: the whole of what the author of an independent
codec is handed (`Suite::encoding_requirements`).

### 3.3 What is held

`check` refuses: a file of another format; an id that is malformed or stated twice; a
requirement with no text or no source; a base source that is not an anchor under a top-level
directory of the upstream checkout; a base requirement none of whose sources is normative for its
aspect, unless it carries an issue; a base requirement with a class; a profile requirement
without a class, a deviation that names no base requirement, and a departure from an id that is
no base requirement; and an `applies` that does not parse or names something other than a support
item of the PICS.

A source is normative for an encoding when it is the protocol definition, its codec, or the key
expression library (which defines the form of a key expression); for a procedure when it is the
protocol definition, the key expression library or the public API's documentation. The
implementation of the transport and of routing is never normative. Whether each anchor still holds
at the pin (the path exists and the needle occurs in it) is the upstream citation gate's, which
grades every tracked file.

### 3.4 Coverage

| Part | File | Covered |
|---|---|---|
| Common encodings, extension chain, batches | `base-transport.toml` | yes |
| Transport: Init, Open, Close, KeepAlive, Frame, Fragment, Join | `base-transport.toml` | yes; the transport OAM is not |
| Network: Push, Request, Response, ResponseFinal, Declare, Interest, OAM; key expressions; what a router forwards | `base-network.toml` | yes |
| Scouting: Scout, Hello | | no |
| Zenoh messages: Put, Del, Query, Reply, Err, and the extensions they carry | | no |
| Service semantics beyond key expressions: the contract sentences of the public APIs | | no |

The transport part has 49 requirements, 11 of them with an issue; the network part 30, 6 with an
issue. Four issues are disagreements between sources: the OpenSyn cookie's length bound
(B-OPEN-2); whether a variable-length integer may be written longer than it needs (B-ENC-2); the
network OAM's header, whose layout and flag constants contradict the codec (B-NOAM-1); and whether
`*` matches an empty chunk (B-KE-3). The rest record rules that only the pinned implementation
states: the resolution negotiation, sequence numbers, lease expiry, the end of a Request, and what
a router forwards and declares.

## 4. The PICS

### 4.1 The proforma

`pics.toml` holds `format = "wz-conformance-pics-proforma"`, `format_version = 1` and one
`[[item]]` per question:

| Field | Holds |
|---|---|
| `id` | `T-` for the transport, `N-` for the network services; upper-case words joined by single hyphens (section 9) |
| `question` | what the implementation answers |
| `status` | ISO/IEC 9646-7's notation: `m`, `o`, `o.<n>` (at least one item of group `n` is supported), `x`, or `c` |
| `condition`, `then`, `else` | for `c`: a selection over other support items, and the status when it holds and when it does not (`n/a` among them) |
| `answer` | `support` (yes or no) or `value` |
| `values` or `min`, `max` | a value item's admitted values, as a list or as an integer range (`max` absent: no upper bound) |
| `unit` | a value item's unit |
| `reference` | the requirements whose selection or value the item decides |

A selection is item ids joined by `and`, `or` and `not`, with parentheses; `and` binds tighter
than `or`. A requirement's `applies`, a conditional item's `condition`, a configuration's, a
primitive's and a test purpose's `selection` are written in it.

### 4.2 What is held

`check` refuses: an id malformed or stated twice; a status outside the notation; a conditional
item without its condition, `then` or `else`, or whose condition names itself; a condition, `then`
or `else` on an item that is not conditional; a group with one item; a support item with values,
a range or a unit; a value item with neither a list nor a range, with both, or with `max` below
`min`; and a reference to no requirement, or to one that does not exist.

### 4.3 wz's answers

A wz build states what it is in its conformance statement (decision C15 of
`docs/build-configuration.md`), and each C ABI library carries the statement's digest, so the
test system can check that the build it talks to is the one the statement describes.
`answers/wz.toml` says, per ABI (`pico`, `c`), how the statement answers each item, in exactly one
way:

| Way | The answer |
|---|---|
| `capability` | supported when the statement says the capability is |
| `limit` | the limit's value |
| `policy`, with `map` | the map's answer for the policy's value; the map names every value the policy takes |
| `fact`, with `map` when the fact's words are not the item's | the protocol fact's value for the ABI |
| `pixit` | the implementation reads the value from its configuration when a session opens, so the PIXIT item named states it for one test environment (ISO/IEC 9646-4's information on the implementation's configuration); `resolve()` puts it in |
| `fixed`, with `why` | the same for every build |
| `unanswered` | what the statement lacks |

A **protocol fact** is what a session of an ABI states on the wire that no switch of the build
declaration moves: the same for every build of the ABI at one catalogue version. The declaration
(`deploy/wz-config.toml`, `[[protocol_fact]]`) gives its value per ABI and where this tree holds
it, as texts that must occur in named files (`holds`) or must not (`lacks`); the statement lists
the ABI's facts beside its values (`facts`), outside the digest, which the ABI and the catalogue
version already fix. The crate's tests read each named file, so a change of the code a fact rests
on is a red test; and `facts_pin.toml` pins the digest of the facts' values at the catalogue
version, so a fact that changes while `catalog_version` does not is a red test too.

| Fact | pico ABI | zenoh-c ABI | Where it is held |
|---|---|---|---|
| `patch` | 1 | 1 | the patch level session-core states in every Init and Join |
| `batch-compression` | no | (the `transport_compression` capability) | the pico crate forwards no compression feature to the session model |
| `request-id-resolution` | 32 | 32 | both engines give every session the code 0b10, and every Init carries its size parameters |
| `router-role` | no | (the `router-node` capability) | the pico ABI opens a client, or a peer for mode peer or a listener; no path of it makes a router |
| `tcp-link` | yes | yes | the tokio engine takes the tcp link in every build; the cooperative engine dials and accepts tcp on a host and on Zephyr |

The statement also names the build's `engine` and `platform`, in its digest (format version 3,
decision C15 of `docs/build-configuration.md`): a pico build on the tokio engine and one on the
cooperative engine, or a host library and a Zephyr one, are different builds even with the same
capabilities. Every PICS item of both ABIs is now answered from the statement or, for the values
the zenoh-c ABI reads from its configuration, from the PIXIT.

`check_answers` refuses a row of another ABI; an item the proforma does not have; a row that
answers in none or several ways; a `why` without a fixed answer or a fixed answer without one; a
map on a row that is neither a policy nor a fact; a capability the declaration does not have, or
does not export for the row's ABI; a limit or policy the declaration does not have; a fact the
declaration does not give for the row's ABI, or whose value, through the map, is not an answer the
item admits; a PIXIT item that does not exist or does not answer in the item's kind (an integer for
a value item, a choice of yes and no for a support item); a capability that answers a value item,
or a limit or policy that answers a support item; a map that does not cover the policy's values
exactly, or maps one to an answer the item does not admit; a fixed answer the item does not admit;
and an item that is not answered exactly once for each ABI.

zenoh-pico 1.10.2 has no router role either: its open reads the configuration's mode as client or
peer and refuses any other value with an invalid-mode error. The pico ABI departs from that: it
opens a client for any mode but peer, `router` included, where zenoh-pico refuses. That is a
parity question of the pico ABI, not of the suite; the fact states what the ABI does.

## 5. The PIXIT

`pixit.toml` holds `format = "wz-conformance-pixit-proforma"`, `format_version = 1` and one
`[[item]]` per question: `id` (`X-`), `question`, `answer` (`text`, `integer` or `choice` with its
`values`), `unit`, and `distinct_from`, another item whose answer this one's must differ from. The
items are the test method; the locators of both ends of the test link; the interface of the test
link and the channel of the test management protocol, which must not be the same interface (a
port of the same interface still shares its queues, its buffers and its processor with the test
link); the values the implementation is configured with where it reads them when a session opens
(`X-IUT-`, section 4.3); the upper tester's share of the implementation's resources; how the test
system slows the test link below the implementation; and the timer tolerance.

`check` refuses an id malformed or stated twice, a choice without values, values on another kind,
and a `distinct_from` that names the item itself or no item.

## 6. What the suite takes from SCE, and what it asks of it

SCE decides the notation and the second executor in its ADR 0091; the TTCN-3 lane lives in a
separate repository (`sce-ttcn3-titan`) under EPL-2.0. wz depends on the surfaces SCE publishes for
it and on nothing else of SCE.

### 6.1 What the suite takes

| Surface | Used for |
|---|---|
| the test profile (`SCE_TEST_PROFILE.md`): the `test-` kinds, templates, ports, timers, defaults, components, verdicts | the abstract test suite |
| features selecting test cases (`--world <feature>,...` of each runner), written `PICS_<NAME>` in the export | PICS support items (section 9) |
| module parameters (`<sce:module-parameter>`, `--module-parameter <id>=<value>`) | PICS value items and PIXIT items (section 9) |
| `sce-codegen export-ttcn3` and `sce-ttcn3-validate` | the TTCN-3 suite and its correspondence check |
| each backend's runner of a generated suite | the native executor |
| the canonical log `sce-test-log.v1` | the comparison of the two runs |
| the recorded input trace `sce-test-trace.v1`, and the downstream's recorder | replaying a live run's inputs into the second executor |
| codec documents (`SCE_FORGE.md`, the codec kind), CBOR among them | the native lower tester's codec, written from the encoding requirements of section 3 and never from wz's message descriptions; and the test management protocol's codec on both executors (section 8) |

### 6.2 What the suite asks of SCE

The first three are taken to a new SCE ADR; the suite waits on it for its lane runs, not for its
writing.

1. **A codec for positional binary messages on the TTCN-3 side.** The lane binds only CBOR and
   content-line formats. zenoh's messages are positional binary with variable-length integers. The
   suite brings its own TTCN-3 types module for them, written clean-room from the encoding
   requirements, encoded by Titan's RAW engine and by external functions for what RAW cannot
   express (variable-length integers, extension chains delimited by a flag). The lane's entry for a
   suite has to be able to name such a consumer codec for a mapped type instead of an SCE codec
   document.
2. **The wire bytes in the trace, decoded on both sides.** A trace record holds the decoded value,
   and in the lane the native side uses no codec. The suite's third condition is that the two
   independent codecs read the same wire bytes to the same value. So a lower-tester port has to
   carry the encoded octets, recorded as such, with each executor decoding them with its own codec,
   and the canonical log recording the decoded value beside them.
3. **A recorded live run.** Against a live implementation the two executors cannot be fed the same
   inputs live. The native executor runs against the implementation, the recorder writes the trace
   (at the octet level of item 2), and the TTCN-3 executor replays it. The recorder must record what
   arrives on every mapped port, the test management protocol's port included.

Settled:

4. **Names.** The existing spellings carry every proforma id; no new grammar is needed (section 9).
5. **The test management protocol's encoding** is CBOR, described by an SCE codec document, which
   the lane already binds on the TTCN-3 side (libcbor).

## 7. Test configurations and purposes

### 7.1 Configurations

`configurations.toml` holds `format = "wz-conformance-configurations"`, `format_version = 1` and
one `[[configuration]]` per test configuration (ISO/IEC 9646-2): `id` (`CF-`), `summary`, `iut`
(the mode the implementation opens its session in: client, peer or router), `selection` (what the
PICS must answer for the configuration to be realisable), and `lower`, the lower tester's
components, each with a `name`, the `role` it takes, its `link` (stream, datagram, multicast) and
its `end` (it `dials` the implementation, `accepts` the implementation's dial, or is in a `group`
with it). The abstract test suite realises each configuration once; a purpose names the one it
runs in.

### 7.2 Purposes

A file of `purposes/` holds `format = "wz-conformance-purposes"`, `format_version = 1`, its `part`,
and one `[[purpose]]` per test purpose, in the structure of ETSI ES 202 553 (TPLan): `id` (`TP-`),
the `requirements` it checks, its `configuration`, its own `selection` beside the configuration's,
the `primitives` the upper tester is reached through, and `with` (the initial condition), `when`
(the stimulus) and `then` (the observation the verdict follows). A purpose says what is checked,
never how or where it runs, and names the lower tester's actions on the wire and the upper
tester's only through primitives. 25 purposes are written, 15 for the transport and 10 for the
network.

### 7.3 What is held

`check_structure` refuses an id malformed or stated twice; an empty summary, `with`, `when` or
`then`; a configuration without components, with a component named twice, or with a component on a
multicast link that is not a group member or the other way round; a selection that does not parse
or names something other than a support item; and a purpose that names no requirement, a
requirement or a configuration that does not exist, or a primitive that does not exist.

## 8. The service primitives and the test management protocol

### 8.1 The abstract service primitives

`asp.toml` holds `format = "wz-conformance-asp"`, `format_version = 1` and one `[[primitive]]` per
primitive, derived from zenoh's services and not from one API: `id`, `code` (its number on the
protocol), `kind` (`request`, which the lower tester asks and one confirm answers, or
`indication`, which the upper tester reports), `selection`, `summary` and `parameters`, each with a
`key` (its key in the protocol's parameter map), a `name`, a `type` (uint, int, bool, text, bytes,
keyexpr, handle, enum with `values`, duration in milliseconds) and whether it is `optional`. An
adapter maps each request to its API family and answers one it has no counterpart for with the
result `unsupported`. The primitives of the advanced publisher and subscriber come with that
part's requirements and PICS items.

### 8.2 The test management protocol

`tmp.toml` holds `format = "wz-conformance-tmp"`, `format_version = 1`, the protocol's `version`,
its `encoding` (`cbor`) and `stream_length_prefix` (`u32-be`), then its messages, its result codes
and its compound procedures. Every message is one CBOR data item (RFC 8949): a map with unsigned
integer keys, key 0 the message's kind. The messages are `hello` and `hello-reply` (the first
exchange: the protocol version, the implementation, its ABI, its statement's digest and its PICS
answers, or a refusal), `command` and its `confirm`, `indication` (with the instant the upper tester
observed it, in nanoseconds of its own monotonic clock), `reset` (to idle), and `procedure` (a
compound stimulus the upper tester runs locally because its timing is finer than a round trip, the
same in every upper tester). Commands carry a sequence number and are carried out at most once;
handles are the upper tester's; the upper tester counts nothing. The result codes are one list for
every implementation, so one cause has one number whichever API family the adapter maps to.

The SCE codec document of the protocol is written from this file, and both executors' codecs come
from it.

### 8.3 What is held

`check_structure` refuses a primitive or procedure code that is zero or used twice; a parameter
key that is zero or used twice, or a parameter name used twice; an enum without values or values on
another type; an encoding other than CBOR or a length prefix other than `u32-be`; a message name
or kind used twice, or kind zero; a field key that is zero (the kind's) or used twice; a protocol
without one of the messages its rules name; a result code used twice; and a result 0 that is not
`ok`.

## 9. Names

The SCE test profile takes a PICS support item as a feature of the suite's feature model (ADR
0057): a feature's name is lower-case words joined by hyphens, and the TTCN-3 export writes each
feature as the module parameter `PICS_<NAME>`, upper-cased with each hyphen an underscore
(`SCE_TEST_PROFILE.md`, the control part). A PICS value item and a PIXIT item are module
parameters of the suite (`<sce:module-parameter>`), whose ids are TTCN-3 identifiers.

Every proforma id is upper-case words joined by single hyphens, so each spelling is one rule and
none loses anything: T-UNICAST is the feature t-unicast and the module parameter PICS_T_UNICAST;
T-FSN-RES is the module parameter T_FSN_RES; X-TMP-CHANNEL is X_TMP_CHANNEL. Being upper-case, no
spelling is a TTCN-3 keyword or a predefined function's name. **No new grammar is needed.**

One collision is left by these rules alone: a value or PIXIT item PICS-T-X would be the module
parameter PICS_T_X, which is also what the export makes of the feature of a support item T-X. So
no proforma id starts with the word PICS; the word elsewhere (T-PICS) is spelled nowhere else and
is allowed. The export refuses a written name that collides with one it makes as well, but the id
is where the collision starts, so it is refused there first. `check` also puts every spelling of
both proformas in one set and refuses two items spelled alike, whatever made them alike (a PIXIT
item with the id of a PICS value item, for one).

## 10. Licence: what lives where (decided 2026-11-14)

**The pieces of the suite that are compiled or linked with the Titan runtime live in a separate
repository under EPL-2.0.** They are: the zenoh TTCN-3 types module, its clean-room positional
codec and external functions, and the test ports in C++. **wz keeps what is not combined with
Titan**: the requirements, the proformas, the answers, the structure of section 7 and 8, the crate
that holds them, and the upper tester, which runs beside the implementation and reaches the lower
tester only through the test management protocol. The repository is made when the first of those
pieces is written.

The basis:

- **SCE's precedent** (`SCE_TTCN3_LANE.md`, sections 2 and 3, in SCE): everything that touches
  Titan is kept in `sce-ttcn3-titan` under EPL-2.0; SCE is run as a program and its files are read,
  so no executable combines SCE's code and Titan's. The suite takes the same split for the same
  reason: one kind of boundary, between programs and published files, on both sides.
- **EPL-2.0's obligations arise when the program is distributed** (section 3.1): the source must be
  available under EPL-2.0, and a distribution under another licence must meet its conditions. A
  test port or external function linked into Titan's executable is distributed with Titan whenever
  the executable is. In an EPL-2.0 repository nothing needs to be checked against wz's own licence
  for that.
- **EPL-2.0's "Modified Works"** excludes works that only contain declarations, interfaces, types,
  classes, structures or files of the Program in order to link to, bind by name or subclass it, and
  a Contribution includes only Modified Works. So wz's own files stay wz's only while they never
  hold Titan's content. Keeping every file that includes or links Titan out of wz makes that true
  by where the files are, not by reading each one.
- The upper tester, the proformas and the answers are never compiled or linked with Titan, so wz's
  licence is unaffected by the lane.

## 11. Steps

The wz side, in order. A step that needs nothing of SCE is marked so.

1. The conformance requirements, base layer, transport part; the PICS and PIXIT proformas for it;
   wz's answers to the PICS. Done (needs nothing of SCE).
2. The base layer's network part, with its PICS items; the PICS items the statement could not
   answer, closed through protocol facts or the PIXIT. Done (needs nothing of SCE); section 4.3
   lists what is left.
3. The test configurations and the first test purposes, transport and network. Done (needs nothing
   of SCE).
4. The abstract service primitives and the test management protocol. Done (needs nothing of SCE);
   the protocol's SCE codec document is written from it next.
5. The other parts of the base layer: scouting, zenoh messages, service semantics, each with its
   PICS items and purposes (needs nothing of SCE).
6. The independent codecs: the TTCN-3 types module, written by a separate author from the
   encoding requirements alone, in the EPL-2.0 repository of section 10; and the native codec
   documents, written from the same requirements by the same rule. Validation by the round trip of
   captures from two or more implementations, and by differential fuzzing of the two codecs (needs
   items 1 and 2 of section 6.2 to run in the lane; the writing needs nothing).
7. The upper tester's common part and one adapter per API family (pico API, zenoh-c API, Rust
   API).
8. The abstract test suite, as test profile documents; the lane entries; the first runs against
   zenoh-pico and wz (needs section 6.2).
