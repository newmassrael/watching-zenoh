# Target build contract: one entry, one manifest

Status: design note, first draft. It states what exists, what is decided and in what
order the work goes; it is not a specification and the atomic store does not parse
it. Every decision here was taken on the standing criterion of this tree: the
long-term correct structure, cost not counted. It is the "Platforms and packaging"
step (step 10) and the `target` axis of `build-configuration.md`, written down as
the contract a consumer's deployment tool can rely on.

## 1. The question

A consumer places wz artifacts on devices of several kinds: an aarch64 Linux board
(Yocto, glibc 2.35), two QNX 7.1 aarch64le boards (one on the io-sock network stack,
one on io-pkt) and an Android arm64 tablet (API 36). Its deployment tool ships, per
node, an executable (or a library) built for that target, and it refuses to ship
what does not match the device or the program that uses it.

How an artifact is built for a target is wz's knowledge: which features a role needs,
which toolchain variables a build reads, what a build links against. The consumer
must not hold a second copy of that knowledge, and wz must not learn the consumer's
deployment rules. The contract between them is therefore two things and nothing
else:

1. an **entry**: one command whose input is a target, a profile and a toolchain
   environment, and whose output is a directory of artifacts and one manifest;
2. a **manifest**: a file that describes the artifacts well enough that the consumer
   reads only it, never wz's build rules and never the artifact itself.

## 2. What exists

Facts read from the tree and measured on one workstation, not claims:

- `wz-capi-pico` builds for `aarch64-linux-android` with the NDK's clang (API 36) as
  a `cdylib`: SONAME `libwz_capi_pico.so`, NEEDED `libdl.so`, `libm.so`, `libc.so`
  only. It is the library a pico C program links; wz ships no pico node executable.
- `wz-ap-demo` builds for the same target as one PIE executable with the same three
  NEEDED entries. The session node and the traffic driver are one binary: the node
  reads a stock zenoh config document through `--config` (build feature
  `zenoh-config`, not in the default `preset-ap-client`), and the traffic a node
  generates is the `driver` key of a `--sessions` session, whose roles are the table
  `sessions_driver::roles::ROLES`, each gated by its own build feature. The binary
  prints its compiled feature set on stderr (`BUILD FEATURES = [...]`, generated by
  its `build.rs`).
- `wz-capi-c` has an ABI revision (`WZ_CAPI_C_ABI_REVISION`), mirrored in its header,
  a gate pin, a Rust `pub const` and a test literal. Before step 1 of §5, `wz-capi-pico`
  and `wz-ap-demo` had no number at all; they now have one each, and all three
  artifacts carry a stamp (T6).
- The pico drop-in's struct layouts depend on capabilities (`multi-thread`,
  `unstable-api` and the two local switches of `build-configuration.md` §2), so a
  program links the library of the arm it compiled its header against. Before step 1,
  nothing in the artifact said which arm it is; the stamp's layout object does.
- `preset-ap-full` does not build for Android in the probe: `librocksdb-sys`'s bindgen
  read the host's headers because the toolchain environment gave it no sysroot. The
  cause is the caller's environment, not shown to be inherent.
- Not tried: any build for aarch64 glibc Linux, any build for QNX, any run on a device.
  `wz-runtime-posix` is `cfg(target_os = "linux")` (empty elsewhere); `platform-qnx` is
  an empty label.
- The vendored zenoh-pico is a submodule of the upstream repository, used as the
  interop counterpart and for `zenoh-pico-sys`; wz carries no patch on it.

## 3. Decisions

**T1. The entry is a verb of `wz-config`, not a new tool.** `package` takes `--target`,
`--profile` and `--out`, resolves the profile into cargo arguments exactly as `build`
does (C1, C9, C14), runs the build and measures the result. Until `wz-config` exists
(step 11) it is a thin script over `wz_config.py`; the command line does not change
when it moves. Rejected: a consumer-specific build script (it would be a second copy
of the cargo mapping), and a manifest written by hand beside each build (it drifts
the first time a feature moves).

**T2. The toolchain environment is the caller's; the entry checks it and records it.**
The entry never selects or downloads a toolchain. It reads the variables the target's
row names (T3), refuses by variable name when one is missing (the bindgen sysroot
above would have been refused at the first command), and records the identity of
what it was given: the rustc release line and the first line of the C compiler's
`--version`, never a path. Rejected: the entry installing SDKs (the lanes of the
owner's machines differ and a licence may bind them).

A cross build also records the identity of its SDK, because that is what tells a
consumer whether an artifact is for its device. `toolchain.sdk` is `null` for a native
build and otherwise an object whose `kind` the platform row declares (`sdk_kind`):
`android-ndk` (IMPLEMENTED: `{kind, revision}`, the `Pkg.Revision` of the
`source.properties` above the compiler the caller's `CC_<triple>` names, so the
manifest holds the value and never the path; the API level is not repeated here, it is
each artifact's `os_floor.android_api_note`, measured from its own bytes), `yocto` (the
SDK version and the target architecture and OS its environment script exports,
recorded as the values of the variables the row names, never as paths) and `qnx-sdp`
(the SDP version the triple names, `qnx710` being 7.1, and the network stack of the row).
The last two are NOT implemented: the entry refuses a platform that names them ("cannot
read a `yocto` SDK yet"), and their shapes were not exercised against a real SDK; the
shape is fixed here so that the lane that first builds for one fills it instead of
inventing it. `--verify` checks that a manifest's sdk kind is the row's and has exactly
the keys the entry writes.

**T3. A platform is a row of the declaration.** `deploy/wz-config.toml` has
`[[platform]]` (not `[[target]]`: the `target` axis of `build-configuration.md` is the
class above, a host Linux or an MCU image, and a platform is one concrete operating
system, libc and triple within it): `id`, `triple`, `os`, `libc` (`glibc`, `bionic`,
`nto`), `network_stack` (QNX only), `std` (`prebuilt`, or `build-std` for a tier-3
triple), the SDK variables beyond those the triple gives (`toolchain_env_extra`), the
facilities the operating system provides (`os_provides`, T9), the system libraries the
row ASSUMES a device has (`system_assumed`, see T5) and the lane that grades it. The
two QNX stacks are two rows with two triples (`aarch64-unknown-nto-qnx710_iosock` and
`aarch64-unknown-nto-qnx710`): the consumer measured that their artifacts cannot be
the same, because the io-sock network library is `libsocket.so.4` (under the io-sock
library directory) where the default SDP has `.so.3`, so the NEEDED entries differ
whatever the code does.

A row is declared and CHECKED against the compiler (`wz_config.py --check`): the triple
must be a target of the pinned rustc, `os` must be its `target_os`, and `libc` what its
`target_os` and `target_env` give. The variables a build reads for the triple
(`CC_<triple>`, `AR_<triple>`, `CARGO_TARGET_<TRIPLE>_LINKER`) are derived from it, so
they cannot drift. A key a row leaves out is NOT ASSESSED, never guessed: of the five
rows only the host row (`linux-x86_64-glibc`, the platform the workspace is built and
tested on) states `os_provides` and `system_assumed` (the latter measured from the
artifacts the entry builds), and Android states `system_assumed` alone (measured on the
probe); the entry refuses a platform it has no such statement for. `lane` is `none` for
all five until a lane's result has been read: Layer C1st exists and passes locally, and
the host row changes in the commit that records its hosted run. Which registered profiles a
platform can build is not a key yet: the mapping from a profile to the artifacts and
their features is step 3's. A platform whose row is absent is refused by the entry with
the reason; it never builds something "close".

**T4. Facts come in three classes and the manifest says which.**

| Class | How it is obtained | Examples |
|---|---|---|
| measured | read from the artifact's bytes by a host tool that never runs the artifact | sha256, size, ELF class and machine, interpreter, SONAME, NEEDED, linking (`static` or `dynamic`), RUNPATH and RPATH (present or absent, with the value), the highest symbol-version tag, the API level in `.note.android.ident`, the ABI stamp (T6) |
| build | recorded by the entry from its own inputs | commit, profile id and version, the resolved features, capabilities and limits, the driver-role table |
| catalog | read from the declaration | platform row, the `os_needs` a capability declares, the lane |

Nothing in the first class is typed by hand. A gate re-measures every artifact the
entry produced and compares it with the manifest, with a deliberately damaged
artifact as its control; a gate that read the value the writer had written would be
one statement checked against itself.

**T5. The closure is closed or refused, and what is "system" is the device's fact.**
Every NEEDED is either `system` (named in the platform row's `system_assumed`) or
`bundled` (a file in the output directory, listed with its own measurements, and the
NEEDED entry names that artifact). An artifact that needs anything else makes the
entry fail naming the library. A `system` entry carries its full SONAME, never a
family name. The row's list is an assumption about a kind of device, not a fact
about a device: the same io-sock stack has been measured with and without
`libc++.so.1` and `libcatalog.so.1` on two boards. The manifest therefore states the
assumption as such, and the consumer, which can ask each device, decides whether a
given device has what the artifact needs. The entry's check stops a build that
needs something nobody assumed; it does not prove any device has it.

**T6. Every artifact carries an ABI stamp, readable without running it.** An ELF note
(section `.note.wz.abi`, owner `wz`, type 1, written by `crates/wz-abi-stamp`) holds
one JSON object with `schema`, `family`, `revision` and, for the C ABI libraries, the
layout arm. A note and not a symbol, as measured: the note is present in the debug
and the release (thin LTO) build of the three artifacts, survives `strip`, and is read
from an `aarch64-linux-android` build on an x86 host; a symbol would have to be
exported from an executable and does not survive stripping. Families: `capi-pico`, `capi-c` (its existing revision,
unchanged) and `ap-demo-surface` (the executable's argument and document surface).
The number is one integer per family, bumped when something a consumer built
against the previous number cannot survive: a removed or renamed door, argument or
document key, or a changed meaning. Additions do not bump it; they appear in the
feature list. The consumer's rule is equality: a mismatch stops and names both
numbers. The single source of each number is a Rust constant, mirrored in the stamp
and in a gate pin (`scripts/lib/abi_stamp_gate.py`), which reads the stamp out of the
built artifacts of both profiles and of a stripped copy; `wz-capi-c` also keeps its
header macro and its door, and the gate holds the stamp to the door's answer. A header
macro and a door for `capi-pico` are not part of the first landing: the drop-in header
carries upstream's symbols only (C10), so they belong in `wz_ext.h`, which is a
decision of its own. The layout arm is a value of the stamp, so a program is told
when it links the wrong arm instead of crashing in a struct it laid out differently:
for `capi-pico` it is `multi_thread`, `unstable_api`, `local_subscriber` and
`local_queryable`; for `capi-c` it is the two switches that move zenoh-c's types,
`unstable_api` and `shared_memory` (`build-configuration.md` §2).
Rejected: reading the number by calling an exported function (it cannot be called
for a foreign target on the build host), an exported symbol (above), and one number
for all families (the headers move independently).

**T7. The manifest is JSON with a schema number, and it is reproducible.** One file,
`wz-target-manifest.json`, at the root of the output directory; UTF-8, keys in a fixed
order. `schema` is an integer; a reader refuses a number it does not know and ignores
a key it does not know; a writer never changes the meaning of a key within a schema
number, and wz tells the consumer before it moves one. No absolute path, no host
name, no timestamp: artifact paths are relative and `/`-separated, and the same
commit, profile and toolchain give the same bytes. Rejected: TOML (the consumer's
tools read JSON already), and a manifest that embeds the build log.

**T8. Roles are what an artifact provides, not file names.** The manifest lists, per
artifact, the roles it provides and how each is reached: `pico-library` (a library
with pico's C ABI), `zenoh-c-dropin` (a library with zenoh-c's C ABI, which a
program the consumer builds links against), `session-node` (an executable that takes
a stock zenoh config document through an argument, present only when the feature is)
and `traffic-driver` (the driver key of a sessions document, with the role words the
build contains). The last is wz's own driver, inside `wz-ap-demo`; it is not the
sibling driver program a consumer links against `zenoh-c-dropin`. A deployment may
use either, and which one is the consumer's decision, so the manifest expresses both
and prefers neither. The role table is emitted by the same generator that already
emits the feature list, so an artifact cannot claim a role its build left out.

**T8a. A floor is recorded as measured, and an unknown floor stays unknown.** The
manifest carries every floor the artifact's bytes give and picks none: for glibc the
highest `GLIBC_x.y` tag (a device is compared through `getconf GNU_LIBC_VERSION`),
for Android the API level of the note and the symbol-version tags, both. QNX has no
version symbols, so its floor is the toolchain identity, which includes the SDP
version (7.1). A floor the entry could not measure is `null`, never a pass; the rule
that turns floors into "this device may run it" is the consumer's.

**T9. Device requirements are derived from the declaration, not measured.** A
capability's `os_needs` (a key of its own: `requires` is the axis condition of C6) is
the set of operating-system facilities it MAY ask for, from a closed vocabulary
(`threads`, `sockets-tcp`, `sockets-udp`, `multicast`, `raw-ethernet`,
`unix-sockets`, `filesystem`, `entropy`, `wall-clock`). It is an upper bound: a device
that lacks one is told which capability to turn off, and it does not say a given
configuration uses it (a TLS plane reads certificate files when its keys name files and
not when they hold the PEM inline). `[os] base` is what every host build asks for
(`threads`, `sockets-tcp`, `entropy`). Every capability states `os_needs`, an empty
list when it asks for nothing beyond the base: a capability nobody assessed has no
entry and `--check` refuses it. The manifest lists the union for the resolved
capability set (`os_needs_of`), and `platform_gaps` names what a platform lacks and
which capability asks for it; a platform with no `os_provides` is unassessed, and the
answer is "unknown", not "none". They are not measured because measuring them means
running the artifact. Memory and stack figures are not in schema 1: they are the
resource gates of step 13 and the manifest names the profile they belong to.

An executable's facilities are not a union over capabilities: the ones that matter there (a
UDP link, multicast, a certificate file) are switched by features of the wz runtime the
executable links, which cargo resolves and the executable's own four features do not list.
So the same discipline is applied one level down. Each feature of `wz-runtime-tokio` is
assessed in `[[runtime_feature]]` for the facilities it may ask for, `--check` holds every
row to a feature the package still declares, and the entry records the features cargo
enabled in that package (`resolved_features`, a build fact, kept so a re-measurement can
recompute) and derives `device_requires` as the base plus those rows. A feature that is
enabled and has no row makes `device_requires` `null`, which means UNKNOWN (never "asks
for nothing", never a pass), and the features nobody assessed are listed in
`unassessed_features`, so a consumer sees which part of the answer is missing. The
core, the codecs and the switchboard schema take no facility of their own (their
sources mention `std::net` and `SystemTime` only in documentation), so only the runtime
package is assessed; a third-party crate's needs are the runtime's, which names the crate
it pulls. The default `wz-ap-demo` enables 54 runtime features, all assessed, and is
`entropy`, `interface-list`, `multicast`, `sockets-tcp`, `sockets-udp`, `threads`. Not
assessed: any runtime feature outside those 54 (the TLS, QUIC, WebSocket, serial,
storage and access-control planes), whose first use in an executable's build is an
`unassessed_features` entry until its row is written. A row is an upper bound read from
the feature's declaration and the modules it gates, not a measurement of a run.

**T10. A refusal writes no manifest.** The entry exits non-zero with the reason on
stderr and removes a partial output directory. The consumer's tool never meets a
half-described artifact.

**T11. A target is only as supported as its strongest green lane.** Lanes are graded
`build` (the entry succeeds and the re-measurement agrees), `run` (the artifact starts
on the target and a session opens) and `interop` (a counterpart exchanges data with
it). The catalogue states the strongest green lane of each target as a fact tied to
`catalog_version`, and the manifest copies it; wz never writes "supported" beside a
target with no lane. Android starts at `build`; the Linux board and both QNX rows are
registered with their lanes at none, and a lane is added when it is first green.

`none` is one word for three different states, so each platform also states `support`,
and the manifest copies it beside the lane: `untried` (no build has been attempted:
the aarch64 Linux board and both QNX rows today), `built` (a build has succeeded, by
hand or by the entry, and no lane has passed: Android, which was built once by hand,
and the host until its hosted run is read), `blocked` (a build was attempted and fails,
and the row's help says why: none today) and `verified` (a lane is green). The
declaration holds them together: `verified` exactly when the lane is not `none`.
"Not supported" is not a state of its own: a platform wz will not build would not have
a row. A consumer that shows a person "not verified" for `none` is right in every case,
and `support` is what tells that person whether anyone has tried.

**T12. The vendored C zenoh-pico is not an artifact of the entry.** wz's replacement
of pico is `wz-capi-pico`; the vendored C library is the interop counterpart, built
on the hosts that can build it, and wire-level interop does not depend on the host
that builds the counterpart. Repairs to its portability (Android's `pthread_cancel`,
QNX's missing headers and rejected `-pipe`) go to the upstream project as changes
there; the submodule stays on an upstream commit with no patch, and a pin moves only
to a commit that has the repair. Rejected: a fork or a patch series in wz's tree (two
copies of the port knowledge, and a conflict at every pin move).

**T13. A registered profile is an input of the entry, and a library is built from it.**
`--profile NAME` takes the NAME of a profile registered under `configs/profiles/` (C14),
never a path, so what a consumer asks for is a versioned contract and not a file anyone
wrote. The entry resolves it strictly with the pinned Kconfig interpreter (C9, C11):
the capabilities that are on once the base original's defaults and the profile are merged,
and the limits it sets off their defaults. A library is then built with no default
features and exactly the features the capability graph gives its ABI for those
capabilities, and the limits are handed to the build as the environment variables the
generated module reads. The manifest records `profile` (`id`, `base`, `capabilities`,
`limits`; `null` for a default build), and `--verify` resolves the profile again and holds
each library to it: a capability the profile turns on that the library lacks, or one it
leaves off that the library has, is a finding, so a manifest cannot name a profile its
files do not hold. A profile does not apply to an executable (the session node's features
are its own and no mapping from capabilities reaches them): asking for it is a refusal.
Measured on the host with the registered client profile: `capi-pico` is 2.8 MB against
5.9 MB for the default build, and its `device_requires` loses `sockets-udp`, `multicast`
and `wall-clock`, which is the reason a profile is an input and not a label.

What the example shows about this build, and does not: the default `wz-ap-demo` has no
`session-node` role because `zenoh-config` is off in `preset-ap-client`, and its driver
roles are the ones its table marks available, read from the file (its facts note). A
library's `device_requires` is the union of what the capabilities its features turn on
may ask for; an executable's is the base plus what the runtime features cargo resolved
for it may ask for, or `null` with the unassessed ones named (see T9). The
glibc floor `GLIBC_2.39` is the host's own, which is the measured reason a library built
on this host does not run on an older glibc: the manifest of a cross build records the
SDK's. The entry does not bundle yet, so a NEEDED nobody assumed is a refusal and `provided_by`
is always `system`; a bundled entry would read `{ "soname": "<...>", "provided_by":
"bundled", "artifact": "lib/<file>" }`. Nothing here was run on a device.

## 5. Steps

Each step lands with its own done-when; sizes are not estimated here. Machines that
belong to the owner (the Yocto SDK host, the QNX licence host) are used only after
the owner approves each use; steps 5 and 6 begin there.

1. **The numbers (landed).** `wz-capi-pico` and `wz-ap-demo` have a revision
   constant, `wz-capi-c` keeps its own, and all three carry the stamp (`wz-abi-stamp`).
   `scripts/lib/abi_stamp_gate.py` (Layer C1st) reads the stamp from the built
   artifacts of both profiles and from a stripped copy, holds it to its pin, and holds
   `capi-c`'s stamp to its door; its selftest drives every failure through a synthetic
   ELF with a clean control. The ELF reader is `scripts/lib/elf_facts.py`. What it does
   not do: a `capi-pico` header macro and door (see T6), and a run of the gate over a
   cross-built artifact in the lane (the stamp of an `aarch64-linux-android` build was
   read once, by hand, as the probe).
2. **The platform rows and the facility table (landed).** `[[platform]]`, `[os]` and
   each capability's `os_needs` in `deploy/wz-config.toml`, validated by
   `scripts/lib/wz_config.py` (`--check` against the pinned rustc, `--selftest` with
   a case for each refusal). What it does not do: state `os_provides` or
   `system_assumed` for any platform but Android's measured libraries (they are
   unassessed, and `--check` lists them), and name the profiles a platform can build
   (step 3 defines the profile-to-artifacts mapping first). The `os_needs` of the 31
   capabilities were assessed from each capability's help text and the code that reads
   files (the TLS, QUIC, user/password and public-key planes, and the timestamp
   source); `scout` is marked `multicast` as an upper bound.
3. **The entry and the manifest (landed on the host platform).**
   `scripts/lib/wz_package.py` builds the named artifacts, measures each file with the
   shared reader (`scripts/lib/elf_facts.py`, extended to the dynamic section, the
   version needs, the Android note and the facts note), writes the manifest and
   verifies it before it returns; `--verify DIR` re-measures every file a manifest
   names; `--selftest` drives each refusal and each finding through a synthetic ELF with
   a clean control, including a changed byte, a replaced file, a hand-edited manifest, a
   stray file and a path leaving the directory. The declaration gained `[[artifact]]`
   and `[[role]]` rows and the host row `linux-x86_64-glibc`, the one platform with
   `os_provides` and `system_assumed` stated. Layer C1st packages the host platform
   twice, requires the two manifests to be the same bytes, and verifies. The schema is
   `shape_findings` (the keys of schema 1, in order, none more) and `verify_dir`, not a
   second description in a schema file: a file would be a second statement of the same
   shape, and the consumer's parser is the fixture of step 7.

   What it does not do yet: bundle a library; take a profile for an executable (T13);
   and "the same bytes" is checked in one build directory, which says the manifest is
   deterministic and not that two machines' builds agree. (The profile input landed after
   this step as T13, and the cross path was exercised by step 4.)
4. **The Android lane at `build` (landed, read on one machine).** Layer C1sp packages
   every cross platform whose row is assessed and whose toolchain variables are set,
   twice per declared artifact, requires the two manifests to be the same bytes and
   verifies the first; the population is the platform rows, so a platform joins by being
   declared and provisioned, not by an edit to the lane. On the owner's workstation
   (NDK 30, API 36) `android-arm64` packages all three artifacts, including `capi-c`
   (which the probe had not tried), needing only `libdl.so`, `libm.so`, `libc.so`, and
   its row is `lane = "build"`, `support = "verified"`. What it is not: a hosted check.
   No hosted job provisions the NDK the row's lane was read with (the runner images carry
   other releases), so there the lane reports the platform as not provisioned and passes,
   and nothing can turn that note into a failure: a switch for it was written first and
   removed, because `armed_skip_guard.py` is right that a flag no job sets is a verdict
   nobody can reach. The green was read on one machine, and the row's help says so; a
   later change that breaks the Android build is seen only where the NDK is, until a
   hosted job provisions that NDK and arms the lane. `os_provides` of the row is what the NDK 30
   headers declare for an API 36 device (not run on one). The `preset-ap-full` bindgen
   refusal of the probe is not exercised: the entry builds default features, and that
   preset is not an artifact. Nothing ran on a device.
5. **The aarch64 glibc lane.** A build with the Yocto SDK, then `run`. Done when the
   binary opens a session on the board and the `system_needed` list is checked
   against the SDK's libraries.
6. **QNX.** The port first (the cooperative host profile on `nto`, entropy and errno
   behind the target; whether the tokio runtime builds for `nto`), then the two
   rows, then lanes. Done when each of the two rows has a lane at `build` and the
   measured NEEDED difference between them (the network library's SONAME) is in the
   rows.
7. **A fixture for the consumer.** One manifest per green target checked in as a
   fixture its tool can parse, regenerated by `--check`, so a schema change is a
   visible diff.

## 5b. The node declaration (proposal, not decided)

A node is a declaration, not an argument vector: which links it dials and listens on, which
multicast groups it joins, which entities it declares (publishers, subscribers, tokens,
queryables, queriers, by key expression), and its budgets. The structure that is correct for
wz is one declaration file per node, registered like a profile, from which the entry (a)
resolves the profile's capabilities exactly as T13 does, (b) turns the budgets into the
`WZ_LIMIT_*` values the generated module already reads, (c) generates the node's entry
crate from the entities and endpoints, and (d) builds it, stamps it and describes it. Each of
(a), (b) and (d) exists; (c) is the missing generator, and the SCE-driven generation the
tree already uses for codecs and switchboards is the precedent for it. What must be decided
before it is written: whether the generated crate targets the heap runtime (a full session
with a daemon-less shape) or the fixed-memory slot profile (no allocator, the kit's node),
since the placing path's per-node budgets read as the second; and what the manifest's role is
for it (a new role beside `session-node`, because its arguments are not a stock config).
