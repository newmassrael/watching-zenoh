# Target build contract: one entry, one manifest

Status: design note, first draft. It states what exists, what is decided and in what
order the work goes; it is not a specification and the atomic store does not parse
it. Every decision here was taken on the standing criterion of this tree: the
long-term correct structure, cost not counted. It is the "Platforms and packaging"
step (step 10) and the `target` axis of `build-configuration.md`, written down as
the contract a consumer's deployment tool can rely on.

## 1. The question

A consumer places wz artifacts on devices of several kinds: an aarch64 Linux board
(Yocto, glibc 2.35), two QNX 7.1 aarch64le boards (one on the io-sock network stack,
one on io-pkt) and an Android arm64 tablet (API 36). Its deployment tool ships, per
node, an executable (or a library) built for that target, and it refuses to ship
what does not match the device or the program that uses it.

How an artifact is built for a target is wz's knowledge: which features a role needs,
which toolchain variables a build reads, what a build links against. The consumer
must not hold a second copy of that knowledge, and wz must not learn the consumer's
deployment rules. The contract between them is therefore two things and nothing
else:

1. an **entry**: one command whose input is a target, a profile and a toolchain
   environment, and whose output is a directory of artifacts and one manifest;
2. a **manifest**: a file that describes the artifacts well enough that the consumer
   reads only it, never wz's build rules and never the artifact itself.

## 2. What exists

Facts read from the tree and measured on one workstation, not claims:

- `wz-capi-pico` builds for `aarch64-linux-android` with the NDK's clang (API 36) as
  a `cdylib`: SONAME `libwz_capi_pico.so`, NEEDED `libdl.so`, `libm.so`, `libc.so`
  only. It is the library a pico C program links; wz ships no pico node executable.
- `wz-ap-demo` builds for the same target as one PIE executable with the same three
  NEEDED entries. The session node and the traffic driver are one binary: the node
  reads a stock zenoh config document through `--config` (build feature
  `zenoh-config`, not in the default `preset-ap-client`), and the traffic a node
  generates is the `driver` key of a `--sessions` session, whose roles are the table
  `sessions_driver::roles::ROLES`, each gated by its own build feature. The binary
  prints its compiled feature set on stderr (`BUILD FEATURES = [...]`, generated by
  its `build.rs`).
- `wz-capi-c` has an ABI revision (`WZ_CAPI_C_ABI_REVISION`), mirrored in its header,
  a gate pin, a Rust `pub const` and a test literal. Before step 1 of §5, `wz-capi-pico`
  and `wz-ap-demo` had no number at all; they now have one each, and all three
  artifacts carry a stamp (T6).
- The pico drop-in's struct layouts depend on capabilities (`multi-thread`,
  `unstable-api` and the two local switches of `build-configuration.md` §2), so a
  program links the library of the arm it compiled its header against. Before step 1,
  nothing in the artifact said which arm it is; the stamp's layout object does.
- `preset-ap-full` does not build for Android in the probe: `librocksdb-sys`'s bindgen
  read the host's headers because the toolchain environment gave it no sysroot. The
  cause is the caller's environment, not shown to be inherent.
- Not tried: any build for aarch64 glibc Linux, any build for QNX, any run on a device.
  `wz-runtime-posix` is `cfg(target_os = "linux")` (empty elsewhere); `platform-qnx` is
  an empty label.
- The vendored zenoh-pico is a submodule of the upstream repository, used as the
  interop counterpart and for `zenoh-pico-sys`; wz carries no patch on it.

## 3. Decisions

**T1. The entry is a verb of `wz-config`, not a new tool.** `package` takes `--target`,
`--profile` and `--out`, resolves the profile into cargo arguments exactly as `build`
does (C1, C9, C14), runs the build and measures the result. Until `wz-config` exists
(step 11) it is a thin script over `wz_config.py`; the command line does not change
when it moves. Rejected: a consumer-specific build script (it would be a second copy
of the cargo mapping), and a manifest written by hand beside each build (it drifts
the first time a feature moves).

**T2. The toolchain environment is the caller's; the entry checks it and records it.**
The entry never selects or downloads a toolchain. It reads the variables the target's
row names (T3), refuses by variable name when one is missing (the bindgen sysroot
above would have been refused at the first command), and records the identity of
what it was given: the rustc release line and the first line of the C compiler's
`--version`, never a path. Rejected: the entry installing SDKs (the lanes of the
owner's machines differ and a licence may bind them).

A cross build also records the identity of its SDK, because that is what tells a
consumer whether an artifact is for its device. `toolchain.sdk` is `null` for a native
build and otherwise an object whose `kind` the platform row declares (`sdk_kind`):
`android-ndk` (IMPLEMENTED: `{kind, revision}`, the `Pkg.Revision` of the
`source.properties` above the compiler the caller's `CC_<triple>` names, so the
manifest holds the value and never the path; the API level is not repeated here, it is
each artifact's `os_floor.android_api_note`, measured from its own bytes), `yocto` (the
SDK version and the target architecture and OS its environment script exports,
recorded as the values of the variables the row names, never as paths) and `qnx-sdp`
(the SDP version the triple names, `qnx710` being 7.1, and the network stack of the row).
The last two are NOT implemented: the entry refuses a platform that names them ("cannot
read a `yocto` SDK yet"), and their shapes were not exercised against a real SDK; the
shape is fixed here so that the lane that first builds for one fills it instead of
inventing it. `--verify` checks that a manifest's sdk kind is the row's and has exactly
the keys the entry writes.

**T3. A platform is a row of the declaration.** `deploy/wz-config.toml` has
`[[platform]]` (not `[[target]]`: the `target` axis of `build-configuration.md` is the
class above, a host Linux or an MCU image, and a platform is one concrete operating
system, libc and triple within it): `id`, `triple`, `os`, `libc` (`glibc`, `bionic`,
`nto`), `network_stack` (QNX only), `std` (`prebuilt`, or `build-std` for a tier-3
triple), the SDK variables beyond those the triple gives (`toolchain_env_extra`), the
facilities the operating system provides (`os_provides`, T9), the system libraries the
row ASSUMES a device has (`system_assumed`, see T5) and the lane that grades it. The
two QNX stacks are two rows with two triples (`aarch64-unknown-nto-qnx710_iosock` and
`aarch64-unknown-nto-qnx710`): the consumer measured that their artifacts cannot be
the same, because the io-sock network library is `libsocket.so.4` (under the io-sock
library directory) where the default SDP has `.so.3`, so the NEEDED entries differ
whatever the code does.

A row is declared and CHECKED against the compiler (`wz_config.py --check`): the triple
must be a target of the pinned rustc, `os` must be its `target_os`, and `libc` what its
`target_os` and `target_env` give. The variables a build reads for the triple
(`CC_<triple>`, `AR_<triple>`, `CARGO_TARGET_<TRIPLE>_LINKER`) are derived from it, so
they cannot drift. A key a row leaves out is NOT ASSESSED, never guessed: of the five
rows only the host row (`linux-x86_64-glibc`, the platform the workspace is built and
tested on) states `os_provides` and `system_assumed` (the latter measured from the
artifacts the entry builds), and Android states `system_assumed` alone (measured on the
probe); the entry refuses a platform it has no such statement for. `lane` is `none` for
all five until a lane's result has been read: Layer C1st exists and passes locally, and
the host row changes in the commit that records its hosted run. Which registered profiles a
platform can build is not a key yet: the mapping from a profile to the artifacts and
their features is step 3's. A platform whose row is absent is refused by the entry with
the reason; it never builds something "close".

**T4. Facts come in three classes and the manifest says which.**

| Class | How it is obtained | Examples |
|---|---|---|
| measured | read from the artifact's bytes by a host tool that never runs the artifact | sha256, size, ELF class and machine, interpreter, SONAME, NEEDED, linking (`static` or `dynamic`), RUNPATH and RPATH (present or absent, with the value), the highest symbol-version tag, the API level in `.note.android.ident`, the ABI stamp (T6) |
| build | recorded by the entry from its own inputs | commit, profile id and version, the resolved features, capabilities and limits, the driver-role table |
| catalog | read from the declaration | platform row, the `os_needs` a capability declares, the lane |

Nothing in the first class is typed by hand. A gate re-measures every artifact the
entry produced and compares it with the manifest, with a deliberately damaged
artifact as its control; a gate that read the value the writer had written would be
one statement checked against itself.

**T5. The closure is closed or refused, and what is "system" is the device's fact.**
Every NEEDED is either `system` (named in the platform row's `system_assumed`) or
`bundled` (a file in the output directory, listed with its own measurements, and the
NEEDED entry names that artifact). An artifact that needs anything else makes the
entry fail naming the library. A `system` entry carries its full SONAME, never a
family name. The row's list is an assumption about a kind of device, not a fact
about a device: the same io-sock stack has been measured with and without
`libc++.so.1` and `libcatalog.so.1` on two boards. The manifest therefore states the
assumption as such, and the consumer, which can ask each device, decides whether a
given device has what the artifact needs. The entry's check stops a build that
needs something nobody assumed; it does not prove any device has it.

Which list a library belongs in is decided by one test: a SONAME is `system_assumed`
when every device of the row's kind has it, because no process starts without it (the
C library, the loader, libm, `libgcc_s` where the compiler's runtime is part of the
base image) or because the kind is defined by it (the network stack's library, which is
why the two QNX stacks are two rows). It is in `bundle_from_sdk` when the SDK ships it
for applications to carry and a device has it only if its image's integrator put it
there: a C++ runtime (`libc++_shared.so` on Android, which the NDK says an app carries;
`libc++.so.1` on QNX and the `libcatalog.so.1` it needs, both measured missing from a
board of the io-sock stack; `libstdc++.so.6` on Yocto, present only when a package of the
image needs it), or any library a device of the kind was measured without. A name is in at most one list
(`wz_config.py --check`), and a row with no `sdk_kind` bundles nothing. A device fact
that contradicts the row (a board without an assumed library) moves the name to
`bundle_from_sdk` in the declaration; it is not an argument of the entry, so one
platform, profile and toolchain always give one package.

When an artifact needs a bundled library, the entry takes the file from the first of the
linker's own search directories that holds it, as the linker driver states them (GCC
and Clang in `-print-search-dirs`; QNX's `qcc`, which answers neither that nor
`-print-file-name`, in the `-L` and `-Y` of the link line `qcc -v` prints), so no list of
SDK directories is kept beside the SDK. It copies its bytes to `lib/<SONAME>`, measures it like an
artifact (sha256, size, the ELF facts) and requires its SONAME to be the name; what it
needs is classified the same way and bundled in turn, so the package's closure is closed
or the entry refuses naming the library. `--verify` re-measures each bundled file, and a
bundled file nothing needs and a `bundled` NEEDED with no file are findings. The entry
does not set a RUNPATH: making the bundled file reachable by the device's loader is the
placing path's, which binds the closure by SONAME. `--sdk-bundle-check ID` reads every
library a row bundles from the SDK, whether or not an artifact needs it today, so the
row is checked against its SDK before the build that first needs it.

**T6. Every artifact carries an ABI stamp, readable without running it.** An ELF note
(section `.note.wz.abi`, owner `wz`, type 1, written by `crates/wz-abi-stamp`) holds
one JSON object with `schema`, `family`, `revision` and, for the C ABI libraries, the
layout arm. A note and not a symbol, as measured: the note is present in the debug
and the release (thin LTO) build of the three artifacts, survives `strip`, and is read
from an `aarch64-linux-android` build on an x86 host; a symbol would have to be
exported from an executable and does not survive stripping. Families: `capi-pico`, `capi-c` (its existing revision,
unchanged) and `ap-demo-surface` (the executable's argument and document surface).
The number is one integer per family, bumped when something a consumer built
against the previous number cannot survive: a removed or renamed door, argument or
document key, or a changed meaning. Additions do not bump it; they appear in the
feature list. The consumer's rule is equality: a mismatch stops and names both
numbers. The single source of each number is a Rust constant, mirrored in the stamp
and in a gate pin (`scripts/lib/abi_stamp_gate.py`), which reads the stamp out of the
built artifacts of both profiles and of a stripped copy; `wz-capi-c` also keeps its
header macro and its door, and the gate holds the stamp to the door's answer. A header
macro and a door for `capi-pico` are not part of the first landing: the drop-in header
carries upstream's symbols only (C10), so they belong in `wz_ext.h`, which is a
decision of its own. The layout arm is a value of the stamp, so a program is told
when it links the wrong arm instead of crashing in a struct it laid out differently:
for `capi-pico` it is `multi_thread`, `unstable_api`, `local_subscriber` and
`local_queryable`; for `capi-c` it is the two switches that move zenoh-c's types,
`unstable_api` and `shared_memory` (`build-configuration.md` §2).
Rejected: reading the number by calling an exported function (it cannot be called
for a foreign target on the build host), an exported symbol (above), and one number
for all families (the headers move independently).

**T7. The manifest is JSON with a schema number, and it is reproducible.** One file,
`wz-target-manifest.json`, at the root of the output directory; UTF-8, keys in a fixed
order. `schema` is an integer; a reader refuses a number it does not know and ignores
a key it does not know; a writer never changes the meaning of a key within a schema
number, and wz tells the consumer before it moves one. No absolute path, no host
name, no timestamp: artifact paths are relative and `/`-separated, and the same
commit, profile and toolchain give the same bytes. Rejected: TOML (the consumer's
tools read JSON already), and a manifest that embeds the build log.

**T8. Roles are what an artifact provides, not file names.** The manifest lists, per
artifact, the roles it provides and how each is reached: `pico-library` (a library
with pico's C ABI), `zenoh-c-dropin` (a library with zenoh-c's C ABI, which a
program the consumer builds links against), `session-node` (an executable that takes
a stock zenoh config document through an argument, present only when the feature is)
and `traffic-driver` (the driver key of a sessions document, with the role words the
build contains). The last is wz's own driver, inside `wz-ap-demo`; it is not the
sibling driver program a consumer links against `zenoh-c-dropin`. A deployment may
use either, and which one is the consumer's decision, so the manifest expresses both
and prefers neither. The role table is emitted by the same generator that already
emits the feature list, so an artifact cannot claim a role its build left out.

**T8a. A floor is recorded as measured, and an unknown floor stays unknown.** The
manifest carries every floor the artifact's bytes give and picks none: for glibc the
highest `GLIBC_x.y` tag (a device is compared through `getconf GNU_LIBC_VERSION`),
for Android the API level of the note and the symbol-version tags, both. QNX has no
version symbols, so its floor is the toolchain identity, which includes the SDP
version (7.1). A floor the entry could not measure is `null`, never a pass; the rule
that turns floors into "this device may run it" is the consumer's.

**T9. Device requirements are derived from the declaration, not measured.** A
capability's `os_needs` (a key of its own: `requires` is the axis condition of C6) is
the set of operating-system facilities it MAY ask for, from a closed vocabulary
(`threads`, `sockets-tcp`, `sockets-udp`, `multicast`, `raw-ethernet`,
`unix-sockets`, `filesystem`, `entropy`, `wall-clock`). It is an upper bound: a device
that lacks one is told which capability to turn off, and it does not say a given
configuration uses it (a TLS plane reads certificate files when its keys name files and
not when they hold the PEM inline). `[os] base` is what every host build asks for
(`threads`, `sockets-tcp`, `entropy`). Every capability states `os_needs`, an empty
list when it asks for nothing beyond the base: a capability nobody assessed has no
entry and `--check` refuses it. The manifest lists the union for the resolved
capability set (`os_needs_of`), and `platform_gaps` names what a platform lacks and
which capability asks for it; a platform with no `os_provides` is unassessed, and the
answer is "unknown", not "none". They are not measured because measuring them means
running the artifact. Memory and stack figures are not in schema 1: they are the
resource gates of step 13 and the manifest names the profile they belong to.

An executable's facilities are not a union over capabilities: the ones that matter there (a
UDP link, multicast, a certificate file) are switched by features of the wz runtime the
executable links, which cargo resolves and the executable's own four features do not list.
So the same discipline is applied one level down. Each feature of `wz-runtime-tokio` is
assessed in `[[runtime_feature]]` for the facilities it may ask for, `--check` holds every
row to a feature the package still declares, and the entry records the features cargo
enabled in that package (`resolved_features`, a build fact, kept so a re-measurement can
recompute) and derives `device_requires` as the base plus those rows. A feature that is
enabled and has no row makes `device_requires` `null`, which means UNKNOWN (never "asks
for nothing", never a pass), and the features nobody assessed are listed in
`unassessed_features`, so a consumer sees which part of the answer is missing. The
core, the codecs and the switchboard schema take no facility of their own (their
sources mention `std::net` and `SystemTime` only in documentation), so only the runtime
package is assessed; a third-party crate's needs are the runtime's, which names the crate
it pulls. The default `wz-ap-demo` enables 54 runtime features, all assessed, and is
`entropy`, `interface-list`, `multicast`, `sockets-tcp`, `sockets-udp`, `threads`. Not
assessed: any runtime feature outside those 54 (the TLS, QUIC, WebSocket, serial,
storage and access-control planes), whose first use in an executable's build is an
`unassessed_features` entry until its row is written. A row is an upper bound read from
the feature's declaration and the modules it gates, not a measurement of a run.

**T10. A refusal writes no manifest.** The entry exits non-zero with the reason on
stderr and removes a partial output directory. The consumer's tool never meets a
half-described artifact.

**T11. A target is only as supported as its strongest green lane.** Lanes are graded
`build` (the entry succeeds and the re-measurement agrees), `run` (the artifact starts
on the target and a session opens) and `interop` (a counterpart exchanges data with
it). The catalogue states the strongest green lane of each target as a fact tied to
`catalog_version`, and the manifest copies it; wz never writes "supported" beside a
target with no lane. Android starts at `build`; the Linux board and both QNX rows are
registered with their lanes at none, and a lane is added when it is first green.

`none` is one word for three different states, so each platform also states `support`,
and the manifest copies it beside the lane: `untried` (no build has been attempted:
the aarch64 Linux board and both QNX rows today), `built` (a build has succeeded, by
hand or by the entry, and no lane has passed: Android, which was built once by hand,
and the host until its hosted run is read), `blocked` (a build was attempted and fails,
and the row's help says why: none today) and `verified` (a lane is green). The
declaration holds them together: `verified` exactly when the lane is not `none`.
"Not supported" is not a state of its own: a platform wz will not build would not have
a row. A consumer that shows a person "not verified" for `none` is right in every case,
and `support` is what tells that person whether anyone has tried.

**T12. The vendored C zenoh-pico is not an artifact of the entry.** wz's replacement
of pico is `wz-capi-pico`; the vendored C library is the interop counterpart, built
on the hosts that can build it, and wire-level interop does not depend on the host
that builds the counterpart. Repairs to its portability (Android's `pthread_cancel`,
QNX's missing headers and rejected `-pipe`) go to the upstream project as changes
there; the submodule stays on an upstream commit with no patch, and a pin moves only
to a commit that has the repair. Rejected: a fork or a patch series in wz's tree (two
copies of the port knowledge, and a conflict at every pin move).

**T13. A registered profile is an input of the entry, and a library is built from it.**
`--profile NAME` takes the NAME of a profile registered under `configs/profiles/` (C14),
never a path, so what a consumer asks for is a versioned contract and not a file anyone
wrote. The entry resolves it strictly with the pinned Kconfig interpreter (C9, C11):
the capabilities that are on once the base original's defaults and the profile are merged,
and the limits it sets off their defaults. A library is then built with no default
features and exactly the features the capability graph gives its ABI for those
capabilities, and the limits are handed to the build as the environment variables the
generated module reads. The manifest records `profile` (`id`, `base`, `capabilities`,
`limits`; `null` for a default build), and `--verify` resolves the profile again and holds
each library to it: a capability the profile turns on that the library lacks, or one it
leaves off that the library has, is a finding, so a manifest cannot name a profile its
files do not hold. A profile does not apply to an executable (the session node's features
are its own and no mapping from capabilities reaches them): asking for it is a refusal.
Measured on the host with the registered client profile: `capi-pico` is 2.8 MB against
5.9 MB for the default build, and its `device_requires` loses `sockets-udp`, `multicast`
and `wall-clock`, which is the reason a profile is an input and not a label.

What `scripts/lib/wz_package.py` writes for the host platform, shortened: the long lists

What the example shows about this build, and does not: the default `wz-ap-demo` has no
`session-node` role because `zenoh-config` is off in `preset-ap-client`, and its driver
roles are the ones its table marks available, read from the file (its facts note). A
library's `device_requires` is the union of what the capabilities its features turn on
may ask for; an executable's is the base plus what the runtime features cargo resolved
for it may ask for, or `null` with the unassessed ones named (see T9). The
glibc floor `GLIBC_2.39` is the host's own, which is the measured reason a library built
on this host does not run on an older glibc: the manifest of a cross build records the
SDK's. The host row bundles nothing (it names no SDK), so `bundled` is empty and every
`provided_by` is `system`. Where an artifact needs a library its row bundles (T5), its NEEDED
entry reads `{ "soname": "libc++_shared.so", "provided_by": "bundled", "artifact":
"lib/libc++_shared.so" }` and `bundled` lists that file, in SONAME order:

```json
"bundled": [
  { "soname": "libc++_shared.so", "path": "lib/libc++_shared.so", "sha256": "...", "size": 9486376,

             "soname": "libc++_shared.so", "runpath": null, "rpath": null,
```

## 5b. The node declaration (decided: the slot profile; landed for Linux)

**Decision (owner, 2026-10-25, on the recommendation):** the generated node targets the
fixed-memory slot profile, not the heap runtime. The first half, below, is `scripts/lib/wz_node.py`
and `deploy/nodes/`; the second half is the entry's build step and the manifest role (what landed
is stated after the structure).

What landed: a declaration file per node (`[node]`, `[[endpoint]]`, `[[entity]]`, `[limits]`,
`[policy]`), validated against the target's own table (`TARGETS`), with `--emit` printing the
`declared.rs` the node's code includes and `--env` printing the `WZ_LIMIT_*` budgets and the
`WZ_POLICY_*` policies. A `[policy]` entry is a policy `deploy/wz-config.toml` declares and a value
it takes (`"on"` or `"off"` for a bool, one of its choices otherwise); the build reads it as the
environment variable that policy's Kconfig symbol names, a policy the node does not state is
upstream's, and the SHA-256 the manifest verifies covers the table because it is the file's. The vocabulary is wider than
the slot target builds (a listener over UDP or TLS, a group over a scheme that is not UDP, a
queryable, querier or token on a node that is a member of a group): a word the target does not
build is REFUSED with its reason, never dropped, so a declaration that asks for a subscriber cannot
produce a node that quietly has none. What the slot target builds today is what its node does: one
dialled endpoint (`tcp`, `udp` or `tls`), one TCP listener, one multicast group, up to four peers
held by their zid (`role = "peer"`, a `zid` and a `tls/` locator: the third transport of decision D7
of `docs/session-lifecycle-intent.md`, the peers a build declares and no verb asks for; `tls` since
only a secure channel proves the node that answered is the one the zid names), queryables that
answer from documents, and the entities below. The registered node,
`slot-answerer`, is the existing `deploy/host-slot-node` stated as data.

**The structure (owner, 2026-10-25: cost ignored, the textbook one): ports and adapters.** The
mechanism is written once (`wz_session_mcu::slot_node`: the storage, the factory, the loop). A
front end owns only what it alone can state, the `static` tables (their sizes are const generics it
chooses) and the way its input becomes a `ClientNode`; the rest is shared. `deploy/host-slot-node`
is one package with a library of what both front ends share (`host_slot_node_glue`: the link's
tuning numbers, the host's console as the node's port, the identity, the secure channel) and two
binaries: `host-slot-node`, whose input is the command line, and `declared-node`, whose input is a
declaration. `declared-node` includes the constants `wz_node.py --emit` prints (the build names
the file in `WZ_DECLARED_RS`), takes its endpoint through the compile-time checked
`StaticEndpoints`, and holds the declaration to the node's limits with `const` assertions, so the
generator's check and the compiler's are two checks and a declaration the node cannot hold does not
build (a declaration whose endpoint is `tls/` does not build without the `tls` feature, and the
reverse). The generated file of each registered declaration is tracked under
`deploy/nodes/generated/`, held current by `wz_node.py --check`, and is what the no-allocator link
gate builds `declared-node` from. Step 1 (landed) moved the parts the two front ends share into the
library without changing the command-line node: its console output for a usage error, an over-long
document, too many documents and a normal start is byte for byte what it was, and no variant
(`get,batching`, `tls`, `declared`, `declared` with `tls`) builds with a warning.

**The entry's step (landed).** A node is an input of the entry, like a profile: `wz_package.py
--artifact declared-node --node ID`. The artifact row of `deploy/wz-config.toml` says `input =
"node"` and names its own manifest and binary, because the package is not a member of the crates
workspace. Before anything is built the entry resolves the declaration (it validates for its
target and its generated file is current), then builds the binary in the package's own directory
with the declaration's features (`declared`, `tls` exactly when a dialled endpoint is `tls/`, `get`, `token` and
`listen` and `multicast` as its entities and endpoints ask), the
generated constants named in `WZ_DECLARED_RS`, the declaration's budgets as `WZ_LIMIT_*` and its
policies as `WZ_POLICY_*`. The
package's own cargo config states the image's budgets, and the generator reads the same file as
the baseline of what the declaration may say, so the generator and the build cannot disagree about
the size of a table. The binary carries the ABI stamp (family `declared-node`) and a facts note
with the node's id and the SHA-256 of the declaration file. The manifest's `provides` repeats both
from the file (role `declared-node`), and what the node asks of a device is the base plus the
sockets its endpoint's scheme uses. `--verify` resolves the declaration again, so a declaration
edited after the build, a file built from another declaration, or a file built with other features
is a finding. The artifact row lists the operating systems its port exists for (`os`): the posix
port exists for Linux and for QNX Neutrino (both stacks, io-pkt and io-sock; `wz-runtime-posix` is
empty on any other OS), so an Android platform row is refused by name, with the reason, before
anything is built. The Neutrino port differs in what the C library lacks: `errno` is read through
`__get_errno_ptr`, the entropy is a read of `/dev/urandom` (the 7.1 library has no `getrandom` and
no `getentropy`, so a node whose random service is not running refuses to start and does not guess),
a socket is made non-blocking by `fcntl` and an accepted connection is made blocking and
close-on-exec by it (the one path for both kernels, since Neutrino has no `SOCK_NONBLOCK` or
`accept4`), a group is joined with `ip_mreq`, and a socket address carries its length. Layer C1sp
reads the Linux aarch64 platform (the glibc 2.35 Yocto SDK) and both QNX platforms (the 7.1 SDP)
with every registered node; each package is verified and the first of a platform is made twice with
the same manifest bytes. The declared nodes were also RUN on four lab boards (2026-10-25, each in one
directory of its own that was removed afterwards): on a Raspberry Pi 4 on aarch64 Linux against a
stock `zenohd` and stock examples cross-built for it from the pinned zenoh source (listener, dialled
tokens, subscriber, publisher, querier, group); on a Raspberry Pi 4 on QNX 7.1 (io-sock), an NVIDIA
Orin board on QNX 7.1 (io-pkt) and an Android 16 tablet against wz's own peer (`ap-demo`), because
the stock `zenohd` and examples do not build for QNX and this repository has no stock build for
Android. Those runs were all on the board's own loopback, plus the group join on its real
interface (the Orin board's in a second, separate run, when the owner said it is a test board).
A third set crossed the boards' real networks: the stock `zenohd` and examples (x86_64) ran on the
lab server, bound to the one address it has on each board's own network, and the five node kinds
that talk to a router or a client (dialled tokens, subscriber, publisher, querier, listener) ran on
each of the four boards against them, built from the same constants with only the address a node
dials, or the one the listener binds, changed in a scratch copy that is not committed. Every leg
passed on every board, which also closes the stock-peer gap for QNX (both stacks) and Android. What
a board run found: the Linux board has one subnet route and no default route, so joining the group
on the interface routing picks failed, and the join now falls back to the first interface that is up
and can multicast. What is still not run: the group against a stock multicast peer on a board (the
Orin board has about a dozen interfaces, and the node joins on the one the stack picks), and the
paced replay's timing on a board.

**The structure of an entity (owner, 2026-10-25: cost ignored, the textbook one).** An entity is a
kind, a key and a BEHAVIOUR, and the behaviours are a closed vocabulary stated as data: a
declaration never carries code, so what a node does with what it receives is one of a few
fixed-memory state machines, each added to the target with its generator rule, its `const`
assertions, its link-gate proof and a witness against the reference router in the same change.
The order is subscriber, publisher, querier, liveliness token, listen, multicast.

**Subscriber (landed).** `kind = "subscriber"`, `key`, `sample_bytes`: the node declares the
subscription on every session and keeps the LATEST sample under it in a cell
(`wz_session_mcu::latest`: the key, the payload cut at `sample_bytes`, how long it was, put or
delete, and a count), in storage the image declares, all zero bytes, so `.bss`. A queryable that
states `from = "<subscriber key>"` instead of `document_bytes` answers from that cell (nothing
while it is empty, and not from a delete), so a node that keeps what it receives and answers
from it is two entities and no code. The node says each new sample on its console, once for each
round that found a cell moved (`HOST-WZ-SAMPLE <key> put len= kept= seq= hex=`, or `<key> del
seq=`), with a count that shows samples that arrived between two rounds. The budgets the entities
decide (`MAX_QUERYABLES`, `MAX_SUBSCRIPTIONS`) follow from them when the declaration states
none, and a declaration that states one below what its entities need is refused. A mirror whose
subscription keeps more than a reply holds is refused. The witness is the reference router's REST
plugin on both sides: a put it routes reaches the subscription, and a get it routes is answered
from the latest sample (`wz_declared_node_zenohd_interop.rs`, which runs the file the entry
packaged).

**Publisher (landed).** `kind = "publisher"`, `key` (a literal key, not a pattern), `period_ms` and
`document_bytes`: while a session is established the node puts a document of that length on that
key, the first put when the session is established and then every period. The session's own
application layer does it, inside its event (`wz_session_mcu::slot_publisher`): after it has
dispatched what the iteration brought it asks a pure schedule what is due, sends each due put,
and tells the drive loop the moment it needs to be awake next, which the loop budgets its wait
by with the transport's own. Nothing runs on the program's main loop and nothing waits in a
mailbox, so the cadence is the session's. A loop that was late sends one put and counts again
from there, a put the session cannot take (between transports) is tried again after 10 ms and is
not counted, and a session that is lost starts over with the next one. The node says what it
published (`HOST-WZ-PUBLISHED <key> sent=<n> refused=<n>`, once for each round that found the
counts moved). A node holds at most four publishers, the size of their schedule in the
session's task cell, and the task cell of a declared node is the larger one. The witness is the
reference router's REST SSE stream: the declared document, eight bytes of `x`, arrives about
every 200 ms, and it arrives again from the next session after the router is stopped and
started (`wz_declared_publisher_zenohd_interop.rs`).

**Querier (landed).** `kind = "querier"`, `key` (a pattern is allowed: it asks for everything
under it), `period_ms`, `timeout_ms` (how long a query may stay pending) and `reply_bytes`: while
a session is established the node asks that key, the first query when the session is established
and then every period, and keeps the latest reply in a cell, the subscriptions' cells' neighbour
in the same storage, so a queryable that states `from = "<a subscriber's or a querier's key>"`
answers from either. A reply that carries data replaces the cell (cut at `reply_bytes`, with how
long it was and a count), a delete replaces it with a delete, an error reply is counted and keeps
nothing, and a query nothing answers ends with its final and leaves the cell as it was. The
layer is the same one the publisher is in (`wz_session_mcu::slot_active`, with the schedule of
`slot_schedule` both are kept on), so a node publishes and asks from one application layer; a
node with a querier is built with the `get` feature and a node without one is not, and the
declaration decides which. The budgets the querier decides follow from it: the pending rows its
queries can fill (the periods that fit in its timeout, and one more) when the image's table is
smaller, and a declaration that states fewer is refused. The node says what it asked
(`HOST-WZ-ASKED <key> asked= replies= errors= finals= timeouts= refused=`) and what it kept
(`HOST-WZ-REPLY <key> put len= kept= seq= hex=`). A node holds at most four queriers. The
witness is the stock `zenoh_z_queryable` as the responder and the reference router's REST plugin
as the asker of the node's own queryable: the reply is kept, it is kept after the responder is
stopped and answered from, another responder's value replaces it, and the node asks again with
the next session after the router is stopped and started
(`wz_declared_querier_zenohd_interop.rs`).

**Liveliness token (landed).** `kind = "liveliness-token"` and `key` (a literal: a token is the
liveliness of one key, and a pattern is refused): the node declares the token on every session as
it establishes, and the router keeps it for as long as the session lasts, tells whoever watches
the key that it appeared, and drops it, with the same word, when the session goes. The node keeps
nothing for it and says nothing of it: a token is only a declaration, recorded after the others
(`DeclarationKind::Token`, sent with `send_declare_token`), so it holds no cell, decides no budget
and is refused nowhere but by a node built without the `token` feature, which refuses to start
with one (`InstallRefused::Tokens`) rather than run and never be heard. That feature is built
exactly when the declaration has a token. The send had no path without an allocator (its owned
form is a heap object): `send_declare_token` now writes the declaration from the caller's text
through the borrowed writer, as the subscriber's and the queryable's do (the writer itself was
already held byte for byte to the owned form), and the owned form and its reconnect cache are the
heap profile's. A node holds at most four tokens, which is the bound the witness runs: four tokens
and a document are the five declarations of one session establishing, and the router sees every
one. The witness is upstream's own pair, which shares no code with wz: `z_sub_liveliness` sees the
four appear when the session is established and dropped when the node is stopped, `z_get_liveliness`
lists them on the pattern that covers them, one on a key that names one and none on a key nothing
declared, and a restarted node declares them again
(`wz_declared_token_zenohd_interop.rs`). The two examples are provisioned beside the others by
`scripts/build-zenohd.sh`, which changes the key of the hosted zenohd cache.

**Listen (landed, TCP).** `[[endpoint]] role = "listen"`, `locator = "tcp/<a.b.c.d>:<port>"` and
`accepts = N` (1 to 4): the node binds that port and takes the connections that arrive, holding at
most `accepts` sessions of them beside the one it dials, if it dials one (a node may only listen:
`DIALS` is then 0 and its table is the `accepts` sessions). The structure is the dial's mirrored,
and the mechanism is written once. In the coop runtime `StreamListen` is the listening half of
`StreamDial` and `Accept` of `Bind`: the stack's acceptor (`IpStack::acceptor`) yields the same
`IpDriver` a dial does, over the stream the listener accepted, claiming its two buffers from the
tables the image declared; a connection that finds none is closed at once and counted
(`IpAcceptor::refused`), and a poll that finds no connection claims nothing. The posix port is
`PosixTcpListener` (non-blocking, `SO_REUSEADDR`, `accept4`), which yields the `PosixTcpSocket` a
dial does. In `slot_client` the node holds the accepted sessions in a table of `accepts` rows
(`Listening<X, N>` names the acceptor and the size together, `Listening::NONE` is a node that
listens on nothing): a pass of its tick frees the rows of sessions that ended, takes what waits on
the port and, if every row is taken, closes the connection before any table is claimed for it
(`refused_over_capacity`); the sessions a node holds are then dialled and accepted alike to
everything it does (declaring, answering, reporting). The identity differs in one respect, and
upstream says which: a client refuses a client (`zenoh/src/net/runtime/region.rs` @
`client-client configuration (invalid)`), so a session a peer opened is met as a PEER while the
routers the node dials still meet a client. A node built to listen carries the accept side of the
handshake, which a client does not (`wz-session-mcu/listen`, forwarded by the image's `listen`
feature): an acceptor given to a node without it would read each InitSyn and answer none, so the
constructor of a `Listening` exists only in a build with the feature, and the declaration decides
the feature. The generator emits `DIALED`, `LISTEN`, `LISTEN_ADDR`, `LISTEN_PORT`, `ACCEPTS` and
`SESSIONS = DIALS + ACCEPTS`, which is the size of the node's session and task tables; the node's
`const` assertions hold the declaration's `listen` endpoint to the feature and to `accepts`. A
UDP listener (it answers the sender of an InitSyn, and the accept loop of the slot node is a
stream's) and a secure listener (the channel of the slot node is one it dials) are refused with
those reasons. A node that holds a session says `session established` when it first holds one and
`session lost` when it holds none, not once for each. The witness has no router in it: upstream's
`z_get` and `z_pub` are clients of the node (`wz_declared_server_zenohd_interop.rs`). It answers
each document byte for byte and nothing for a key it does not serve; two stock clients hold the
two sessions and a third is refused by a connection closed at once, a freed row serves the next
client, and the holder that stayed is not disturbed; two connections that say nothing are closed
at the handshake deadline and free both rows. Presenting a client to the accepted sessions fails
all three, which is what ties the identity to the witness.

**Multicast (landed, publishers and subscriptions).** `[[endpoint]] role = "multicast"`, `locator =
"udp/<group>:<port>"` (an address from 224.0.0.0 to 239.255.255.255), `members = N` (1 to 8: the
members of the group the node tracks at once, a row of the group's peer table each) and an optional
`ttl` (1 to 255, default 1, the kernel's and zenoh's own). A group has no handshake and no session
with anyone: a member announces itself with a JOIN beacon, admits the members whose beacons it
hears and puts what it publishes on the group for all of them, so the node's plane is one task, not
a session. The structure is the listener's again, written once. In the coop runtime
`GroupTransport` already was the seam (lwIP's and Zephyr's implement it), and the posix port is
`PosixGroupTransport`: the shape zenoh gives a multicast link, two sockets, a receiver bound to the
wildcard address on the group's port with `SO_REUSEADDR` and `SO_REUSEPORT` (so it shares the port
with every other member on the host) and joined, and a sender on a port of its own, so the source a
peer sees names this member and no other even when two live on one host. In `wz-session-mcu`
`slot_plane` is the node's whole knowledge of anything it takes part in beside its sessions
(`Plane`, `PlaneRunning`, `NoPlane`), `ClientNode` holds one as a value as it holds its acceptor, and
`slot_group` is the group: the pump of `group_drive` in a cell of a `MulticastSlots` table the image
declared, its datagrams fanned as the same `IterationEvent`s to the same observer the sessions
dispatch to (so a subscription keeps the latest sample of any member's put in the same cell), the
node's publishers put on the group by the same `Schedule` that puts on a session and counted in the
same counts, the members counted from the arrivals and departures the pump reports, and a rejoin a
second after the group is lost or could not be joined. The parameters a group's members must agree
on (the sequence-number resolution `0x02` and the 2,048-byte batch) are the stock peers' own, since
a JOIN that advertises others is refused and nothing negotiates. The generator emits `GROUPS`,
`GROUP`, `GROUP_ADDR`, `GROUP_PORT`, `GROUP_TTL` and `MEMBERS`; the `multicast` feature is built
exactly when the declaration has the endpoint, and the node's `const` assertion holds the two to each
other; `TASKS` is the sessions and one for the group. What a group carries with no allocator is the
literal Put: the replies of a queryable, the Request of a querier and the answer a token gives to
an interest are heap-only forms in the shared emit, so a node that is a member of a group may
declare publishers and subscriptions and the validator refuses the other kinds for it, by name,
rather than serve them on its sessions and drop them on the group. The node says `HOST-WZ-GROUP
<locator> joins=<n> refused=<n> turned_away=<n> members=<n>` each time any of the four moves;
`turned_away` counts the JOINs its member table had no free row for in the current join (a peer
turned away announces itself again each join interval, so it counts beacons and not peers), which is
how a lab tells a full table from a node that stopped taking members. One set of peer
tables serves the whole group, so an alias a member declares is an id of the group: a put that names
its key in full, which is what zenoh-pico's multicast peer sends, is unaffected, and two members that
alias different keys under one id are not told apart. A put longer than one frame arrives as a
Fragment chain (zenoh-pico cuts at the link's MTU, about 1,470 bytes, before it cuts at the batch),
and the `group` feature turns on the router that stages a chain per member
(`reassembly`, with `transport-fragmentation`'s fragment codec): the chain is put back together and
the subscription's cell keeps what it holds of the whole, and the line says the whole length. A chain
past the reassembly slot (4,096 bytes) is dropped whole. The router is about 22 KiB of the image's
`.bss`, which is what the feature costs a node that is a member of a group; a build with no group
does not carry it. The witness is zenoh-pico's own multicast peers
(`wz_declared_group_pico_interop.rs`, Layer M, since a multicast route is the host's): a pico
`z_sub` hears the node's eight-byte document more than once and a `z_sub` of another key hears none;
a pico `z_pub`'s puts reach the node's subscription, which keeps the latest, and a put on a key the
node does not subscribe to is kept by nothing; the node counts its members, none, one while pico
is there and none again once its lease has run out; and a pico `z_put` of 1,000 bytes is kept whole,
one of 3,000 (a chain) is reassembled and one of 5,000 is dropped, after which the node still takes
the next. Advertising another sequence-number resolution fails the first three, which is what ties
the group's parameters to the witness, and building without `reassembly` fails the fourth at the
chain, after its whole-frame put passed, which is what ties the reassembly to it.

Not written: the group's queryables, queriers and tokens, each of which is a change to the shared
group emit (an allocator-free Response, Request and DeclareReply) before it is a word a node with a
group accepts (no stock peer answers a query over a group at all: neither zenoh-pico, with or
without its multicast declarations, nor zenoh's own, so there is nothing to prove one against);
peer tables of each member; a UDP or a
secure listener; declarations toward accepted peers that are not clients (they are sent as to the
router today, and no peer has judged them); a port of the declared node for QNX or Android; and the
budgets that are still tuning constants of the library (the task cells, the receive and send
storage), which the declaration cannot state.

The text below is the proposal the decision answers.

A node is a declaration, not an argument vector: which links it dials and listens on, which
multicast groups it joins, which entities it declares (publishers, subscribers, tokens,
queryables, queriers, by key expression), and its budgets. The structure that is correct for
wz is one declaration file per node, registered like a profile, from which the entry (a)
resolves the profile's capabilities exactly as T13 does, (b) turns the budgets into the
`WZ_LIMIT_*` values the generated module already reads, (c) generates the node's entry
crate from the entities and endpoints, and (d) builds it, stamps it and describes it. Each of
(a), (b) and (d) exists; (c) is the missing generator, and the SCE-driven generation the
tree already uses for codecs and switchboards is the precedent for it. What must be decided
before it is written: whether the generated crate targets the heap runtime (a full session
with a daemon-less shape) or the fixed-memory slot profile (no allocator, the kit's node),
since the placing path's per-node budgets read as the second; and what the manifest's role is
for it (a new role beside `session-node`, because its arguments are not a stock config).
